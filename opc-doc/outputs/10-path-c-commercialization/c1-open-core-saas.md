# 路径 C1 展开方案：免费自托管 + 付费 Pro 云（Open-core 模式）

> 状态：方案设计（未投入执行，先过验证线）
> 承接：path-c-research.md（C1 概念）· path-c-segments-content-tmc-events.md（B 端延伸）
> 调研证据：2026-09-25

## 一、产品定义（Open-core）

一句话：**代码全开源（MIT，可自托管），云上卖托管与高级能力。**

| 层 | 形态 | 差异化 |
|---|---|---|
| 开源核心（MIT） | 现状仓库即全部：多 Agent 规划 / diff 修订 / 质检 trace / 协作分享 / 笔记导入 / Plan B | 已成，零新投入 |
| 云免费层 | 部署在云上的同一套（免去用户自托管） | 免运维的"便利费" |
| Pro 付费层 | 额度解锁 + 高级能力 + 数据与协作增强 | **付费的核心** |

## 二、功能分层（关键决策：付费墙划在哪）

| 能力 | 开源/自托管 | 云免费 | Pro（付费） | 理由 |
|---|---|---|---|---|
| 多 Agent 规划 | ✅ | 3 次/月 | ♾️ | 次数是天然计量单位，锚定订阅 |
| diff 对话式修订 | ✅ | ✅ | ✅ | 差异化核心，不锁（护口碑） |
| 质检 trace / T-A-O | ✅ | ✅ | ✅ | 不锁（护信任） |
| 分享 / 评论 / 投票 | ✅ | ✅ | ✅ | 病毒钩子，不锁 |
| 笔记导入 / Plan B | ✅ | ✅ | ✅ | 获客钩子，不锁 |
| 画像记忆 | ✅ | ✅ | ✅ | 不锁 |
| **无限规划 + 优先级队列** | ❌ | ❌ | ✅ | 直接对应 token 成本，最合理付费点 |
| **多人协作 Pro（邀请人数/行程数上限、实时同步）** | ❌ | 有限 | ✅ | Wanderlog 已验证付费点 |
| **高级导出（无品牌/多格式/高清图）** | ❌ | 有品牌 | ✅ | 低摩擦转化 |
| **城市攻略数据包 / 本地生活深度** | ❌ | ❌ | ✅ | 内容型差异化（后续，非第一版） |
| **旅行中助手（行中改签/天气/记账/地图**兜底**）** | ❌ | ❌ | ✅ | **真正的高频场景（见硬伤一）** |

## 三、定价模型（基于 2026 调研锚点）

- 国内 AI 工具订阅锚点：**¥9.9/月**（火山方舟、DeepSeek 等 9.9 元月费已成常态）；2026 年 5 月起出现"集体涨价"趋势（免费额度收紧，付费化被教育）。
- 国外规划工具锚点：Wanderlog **$39.99-49.99/年**（不能按旅游低频卖高频价）；Layla $9.99/月。
- **建议定价**：
  - Pro 月付：**¥19.9/月**（锚点略高于 9.9，给按年留空间）
  - Pro 年付：**¥128/年**（约 ¥10.7/月，首年锚定 ¥88 促销）
  - 首发促销：¥88/年前 100 名（冷启动期）

**成本模型（诚实测算）**：
| 项 | 量级 | 说明 |
|---|---|---|
| DeepSeek 一次完整规划（4 Agent + 多轮校验+质检） | ~¥0.05-0.15 | 主要成本 |
| 服务器（云免费层，单实例） | ¥50-100/月 | 一台 2C4G 起步 |
| 免费层 3 次/月 × 1000 活跃 | ~3000 次 | 约 ¥150-450/月 LLM 成本 |
| Pro 客单 ¥128/年 | 需覆盖成本 | 转化率 2-3% 即打平 |
| **结论**：免费层成本可承受（千级活跃内），Pro 转化 2% 以上即盈利。**早期不烧钱。**

## 四、三个硬伤与对策（CPO 必答）

### 硬伤一：旅行规划是低频场景，订阅付费意愿天然低
- 用户一年规划 2-3 次 → 为"每月无限次"付费的动机弱。
- **对策**：付费点从"规划次数"转向"行前→行中→行后全程"：
  - 行前：规划 + 修订 + 协作（低频）
  - **行中：实时改行程、天气、记账、地图（高频）→ 这是 Pro 真正的价值**
  - 行后：游记/回忆册导出（强情感价值）
- **验证**：如果 demo 用户行中使用 > 30%，Pro 成立；否则只做"次数+协作"薄付费。

### 硬伤二：开源与付费存在"自己部署就不花钱"的内在矛盾
- MIT 全开源 → 技术用户自己部署，永远不付费。
- **对策**：这不是 bug，是漏斗——自托管者是**影响力/传播节点**（文章、教程、口碑），付费者是**非技术大众**（不想部署、不会配 key）。PostHog/Supabase 已验证：开源核心 + 云托管照样跑。
- **代价**：开源项目可能被白嫖商用（MIT 允许）。**接受**：这是"规划层透明定位"的既定策略（见文章 07），先要影响力和信任，再谈变现。

### 硬伤三：无流量，冷启动鸡生蛋
- 0 用户 → SaaS 没有地基。
- **对策**：C1 **必须**排在主线 A（文章 + 开源）之后。文章验证 A 信号（收藏 >50 / 有人问代码）→ 才有第一批种子用户 → 才谈付费墙。

## 五、验证路线（先验证再建 SaaS，不上来就付费墙）

| 阶段 | 动作 | 产出/信号 | 判定 |
|---|---|---|---|
| P0（本周-2周） | 部署公开 demo（deploy/ 已 ready）+ 一页 landing（免费试用 + Pro 预订） | 可访问的 demo URL | —— |
| P1（2-4周） | 文章①发布 + demo 引流 | 50-100 真实用户 | 看行为 |
| P2（4-8周） | 埋点观察：规划数/修订数/分享数/行中留存 | 协作与修订使用率、周留存 | 见判定线 |
| P3（信号通过） | 付费墙 A/B：免费 3 次/月 → 提示升级 Pro（¥19.9/月 或 ¥128/年） | 转化率 | ≥1% 继续，<1% 回退 |
| P4（转化通过） | 加"行中助手" Pro 功能（最快差异化） | 行中使用率 | 见硬伤一 |

**判定线（写死，达不到就回主线 A）**：
| 信号 | 线 | 动作 |
|---|---|---|
| demo 周活跃用户 | <50 | 回主线 A，不建 SaaS |
| 协作/修订使用率 | <30% 用过一次 | 说明没抓住真实需求 |
| Pro 转化率（P3） | <1% | 回退免费，继续攒量 |
| 行中使用率 | <30%（若有） | Pro 定位回退到"次数+协作" |

## 六、与其它路径关系

- **主线 A（内容/开源）** = C1 的燃料（流量与信任）。**C1 不先于 A 启动。**
- **C2（B 端白标/会展）** = C1 的能力复用出口（同一套引擎）。C1 的 demo 就是 C2 的 POC 素材。
- C1 验证出"有人为规划付费"= **给 C2 的 B 端报价提供筹码**（"消费者市场已验证"）。

## 七、落地检查清单（真正启动时）

- [ ] 公开 demo 部署 + 域名 + HTTPS（nginx 已就绪，需公网）
- [ ] 埋点：规划/修订/分享/投票/留存（后端已存 task/trip，需加事件表）
- [ ] Landing 页（免费试用入口 + Pro 预订按钮 + 企业版入口）
- [ ] 付费墙：3 次/月限额 + 升级页（支付：微信/支付宝，需主体/商户号）
- [ ] Pro 功能第一版：无限规划 + 无品牌导出 + 协作上限放宽（全是已有代码的配置项，**零新开发**）
- [ ] 行中助手（若 P3 通过）：移动端简版（行中改行程/天气/地图）——**这是最大的新开发项，非第一版**

## 结论

C1 是**可行的第二曲线，但不是第一步**。正确顺序：先用主线 A 攒流量与信任 → 部署公开 demo 低门槛验证 → 行为信号过线后才上付费墙。**C1 的第一版付费墙 = 零新开发**（现有功能的配额/导出/协作上限解锁），全部是配置；真正的新开发（行中助手）留到验证之后。
