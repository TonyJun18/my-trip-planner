# 付费点设计报告：从「卖次数」到「卖这一次别出错」

> 日期：2026-11-06
> 承接：`c1-open-core-saas.md` §二「功能分层：付费墙划在哪」、`path-c-research.md` §二「市场证据」
> 状态：方案设计（未验证，不构成立即投入）
> 依据：仓库现状代码勘探（2026-11-06，`backend/app/services/` 全量过读；全仓无 payment/billing/stripe 代码）

## 摘要

1. **低频场景不该卖订阅次数。** 一年规划 2–3 次的用户，对「每月无限次」几乎无感（`c1` 已论证为硬伤一）。真正能收钱的是**一次性、高感知、发生在痛点峰值**的商品。
2. **付费锚点应从「软件月费」换成「行程总价的 1%」。** 一趟 3k–30k 的旅行，¥19.9–69 是零头的零头；而 ¥19.9/月的订阅会触发「我用得回本吗」的算账心理。
3. **本报告给出 7 个付费点，按「舍得程度」排序。** 第一梯队 3 个（行中救急 / 踩坑体检 / 省钱报告）全部建立在已落地服务之上，其中**踩坑体检零新开发**。
4. **首选落地项：¥19.9「行中安心包」**（出行前 24h 推送，按行程售卖、行程结束失效）。它是唯一同时满足「代码 90% 已有 / 零 LLM 成本 / 痛点峰值 / 一次性付费无订阅抵触 / 开源项目偷不走」的路径。
5. **共同前置缺口是支付基建**——仓库当前没有任何支付/账单代码。三个候选方案都卡在微信/支付宝商户主体这一步。

## 一、判断框架：旅游用户到底为什么付费

### 1.1 三个付费动机，只有一个属于我们

| 动机 | 典型产品 | 与本项目关系 |
|---|---|---|
| 省下更多钱（可计算 ROI） | 比价、返利、优惠券 | **弱相关**——没有真实价格与库存数据 |
| 避免大额损失（保险心理） | 行程保险、风险体检 | **强相关**——校验能力已建成，只是没商品化 |
| 省下心力 / 少吵架（情绪价值） | 协作、代做、送礼 | **强相关**——协作与分享能力已建成 |
| 提高产能（替代工时） | 内容工具、SaaS | 相关但客群窄（B 端创作者） |

规划本身属于「提高效率」，而**效率在低频场景里不值钱**——这是所有 AI 旅行工具付费失败的共同原因。可以收费的不是「帮你规划」，是「帮你不出事」。

### 1.2 付费意愿公式

```
付费意愿 ≈ (省下的钱 + 避免的损失 + 省下的心力) × 价值可见度 ÷ 支付时的摩擦
```

三个可用杠杆：

- **抬高分子**：把「风险」和「可省金额」显式算成数字（不是「已为你优化」，而是「这趟有 3 个坑，可能白跑一天」）。
- **抬高价值可见度**：在用户看到风险的同一屏收费，而不是在首页挂订阅。
- **压低摩擦**：一次性付款、按行程计价、不绑卡、不退订流程。

### 1.3 时机 > 功能（moment-based paywall）

同一个功能放在不同时刻，转化率差一个量级。本项目有四个天然的高转化瞬间：

| 时机 | 用户心理 | 可卖什么 |
|---|---|---|
| 质检报告弹出「发现 3 个风险」之后 | "原来我差点白跑" | 一键修坑 / 踩坑体检升级版 |
| 出行前 24 小时 | "明天就走了，别出事" | 行中安心包 |
| 导出 / 分享给同行者之前 | "要发给人看，得体面" | 精美版 / 去品牌 |
| 行程中真的出现异常 | "现在就要解决方案，多少钱都行" | 行中救急（按次） |

**反模式**：首页订阅墙、注册即付费墙、把「AI 次数」做成首屏卖点（等于把 token 成本摆到用户面前让他算账）。

## 二、七个付费点全景

排序依据 = 付费意愿强度（痛点峰值 × 损失量级 × 决策速度），非实现难度。

| # | 付费点 | 谁付钱 | 建议价 | 代码复用 | 新增工作量 | 付费强度 |
|---|---|---|---|---|---|---|
| 1 | 行中安心包 / 救急 | 行程中的旅行者 | ¥19.9–29.9 / 行程 | live / revise / weather / PlanB / PWA | 中（移动端+推送） | ★★★★★ |
| 2 | 出行前踩坑体检 | 出发前的决策者 | ¥9.9 / 次 | dynamic_facts / TimeGate / DrivingGate / exertion / multi_city | **极低**（包装+支付） | ★★★★☆ |

| 4 | 代做 / 送礼包 | 子女、朋友（非旅途中） | ¥39–69 / 份 | export / checkin / 打包清单 / 分享链接 | 低（老人模式排版） | ★★★★☆ |

## 三、第一梯队详解

### 3.1 行中安心包（首选）

**场景痛点**
行程进行中出状况：暴雨、景区临时闭园、高铁延误、同伴体力不支、临时想改半天。此时用户面对的真实替代方案是「自己重排一遍 + 跟同行的人吵一架 + 白跑一趟」。

**商品定义**
按 `trip_id` 售卖的「行中能力解锁包」：

- 今日视图 + 打卡 / 跳过 / 一键顺延（今天来不及了）
- 异常时的替代候选（附近可换的景点 / 餐厅 / 室内方案）
- 变更后自动重算预算与后续日程
- 变更通知同行者（事件流 + PWA 推送）

**为什么舍得**
支付发生在焦虑峰值，且金额相对于「浪费一天行程 + 同行者情绪」可以忽略。这是本报告里**决策速度最快**的付费点。

**现有代码复用（关键：核心逻辑已建成）**

| 能力 | 位置 | 状态 |
|---|---|---|
| 行中状态机（upcoming/live/finished） | `services/live_service.py: live_status` | ✅ |
| 打卡 / 跳过 | `check_stop` / `skip_stop` | ✅ |
| 一键顺延（整体挪到明天） | `delay_today`（复用 revise 原子内核 + DrivingGate + 预算重算） | ✅ |
| 对话式改行程（可回滚） | `services/revise_service.py: _apply_diff` | ✅ |
| 确定性备选方案 | `services/plan_b.py` | ✅ |
| 天气 | `agent/tools.py`（高德 / wttr.in 降级） | ✅ |
| 变更通知 | `services/event_service.py` + `services/ws_broadcast.py` + PWA Notification | ✅ |
| 行中费用与分摊 | `services/expense_service.py` | ✅ |
| 打卡徽章（黏性） | `services/passport_service.py`（7 条规则） | ✅ |

**缺口**
移动端体验（当前为桌面 Web，而行中付费恰恰发生在手机上）、实时延误数据（航班/高铁状态）、支付与授权校验（按 trip 维度的 entitlement）。

**定价与计量**
- ¥19.9 基础包（顺延 + 替代候选 + 通知）/ ¥29.9 完整包（+ 无限次救急 + 费用分摊）
- 出行前 24h 推送开通，`trip.end_date` 后自动失效（避免「我买了没用到」的退款争议）

**为什么这一项与开源不冲突（结构性优势）**
`c1` 硬伤二指出「MIT 全开源 → 技术用户自己部署」。但行中能力依赖**常驻服务 + 推送通道 + 多端同步**，自托管者的体验天然残缺。付费点长在「托管运行」而不是「代码功能」上，这恰好避开了 open-core 的内在矛盾。**这是本报告认为它应作为第一付费点的最重要原因。**

**验证信号**
开通率（出行前推送 → 开通）≥ 8%；行中功能使用率（打卡/顺延/跳过任一）≥ 30%；行程结束后 30 天内复购下一趟 ≥ 15%。

### 3.2 出行前踩坑体检（最快能上线）

**场景痛点**
用户辛苦规划的行程里藏着「周一闭馆」「自驾单段 180km」「第 4 天累计游玩 9 小时」「假期限流」这类硬伤。酒店门票多数不可退，代价是**白跑一天**。

**商品定义**
一份结论式报告，不是「已为你优化」的模糊承诺，而是可数、可验证的清单：

> 本趟 5 天，发现 4 个高风险：
> ① D2（周一）博物馆闭馆 —— 建议与 D3 对调
> ② D3 自驾单段 180km / 预计 2h50m，超单段上限（120km / 150min）
> ③ D4 累计游玩 9h20m，超体力阈值（>480min）
> ④ D5 跨城衔接缓冲不足 40min
> 影响：其中 ②④ 可能导致当晚住宿作废。

下面一行转化按钮：**「¥9.9，把这 4 个坑全部修掉」**。

**为什么舍得**
保险心理。用户怕的不是花钱，是把不可退的酒店钱扔在路上。¥9.9 对比潜在损失 3000+，是典型的小额高杠杆。

**现有代码复用（近乎 100%）**

| 校验 | 位置 | 产出 |
|---|---|---|
| 营业时间 / 游玩时长 / 过饱和 | `services/time_validation.py`（TimeGate，MAX_STOPS_PER_DAY=5、MAX_PLAY_MINUTES_PER_DAY=480） | warning + 调整建议 |
| 自驾距离 / 时长 / 累计里程 | `services/driving_service.py`（DrivingGate，120km / 150min / 300km） | critical 级问题 |
| 周一闭馆 / 免费日 / 节假日窗口 | `services/dynamic_facts.py` | 特例命中 warning |
| 体力负荷 | `EXERTION_BY_TYPE` + 名称关键词规则库 | 累计负荷超限提示 |
| 多城市衔接 | `services/multi_city.py` | 缓冲不足 warning |
| 质检总评 | `agent/agents.py: TravelCriticAgent` | 四维评分 + issues |

**缺口**
几乎为零。需要的是：把分散在各处的 warning 聚合成一份「面向用户的报告」（可复用质检卡通道）、一个支付入口、以及「修掉」动作的编排（调 `revise_service` 逐条应用）。

**定价**
¥9.9 单次，或打包进「踩坑体检 + 行中安心包」¥29.9。

**诚实口径**
所有条目 `basis=rule_based`，报告里必须标注「以现场为准，出行前请再次确认」——这既是项目既有哲学，也是免责需要。

**验证信号**
报告页 → 支付的转化率 ≥ 5%；支付后「修掉」点击率 ≥ 50%（说明真的是痛点而非好奇）。

### 3.3 省钱报告（唯一能算 ROI，但当前数据不够硬）

**商品定义**
把预算与优惠规则算成一张账单式结论：「本趟可省 ¥680」，逐项给「怎么省 + 去哪办」。

**现有代码复用**
`services/budget_service.py`（分类汇总 + 大交通估算 + 城市基准价）、`services/discount_service.py`（城市级/证件级确定性规则库）、`services/servicing_service.py`（定稿后 servicing 阶段，`DiscountAnalysisAgent` 走 Tavily 且「无来源即丢弃」硬闸门）。

**关键限制（必须写清）**
`discount_service` 的设计哲学是**只输出高置信度普遍规则**（学生证、老年证、旅游年卡、平台通用优惠），明确不做实时比价。因此当前能卖的只有「规则级省钱」，卖不了「同房型全网最低价」。

- 规则级省钱 → 价值上限约 ¥100–300/趟，定价 ¥9.9 合理。
- 真比价 → 需接 OTA 联盟 / 门票分销 API，属于独立工程线，**不应作为第一版收入来源**。

**定价与转化逻辑**
免费给「可省金额」摘要（制造锚点），付费解锁「逐项怎么省 + 办理入口」。省 680 收 9.9 是唯一不需要解释付费理由的定价。

## 四、第二梯队详解（要点）

### 4.1 代做 / 送礼包（孝心溢价）

**付费者与使用者分离**——这是最被忽略的结构性优势。子女给父母做行程，付费动机是「我不在旁边也放心」，价格不敏感；且收礼的人会问「这谁做的」，天然裂变。

**商品形态**：¥39–69/份「安心行程包」= 大字版 PDF + 每天最多 2 站（复用体力与时间阈值）+ 附近医院/药店 + 紧急联系人 + 入住指引（`checkin_service`，不收集证件号）+ 一键导航 + 打包清单 + 免登录分享链接（`collab_service` 的 share_token）。

**复用**：导出（`export_service.py` + 前端 `TripDetailMoreMenu` 的 PDF/图片/打印）、`checkin_service`、打包清单、`collab_service`。新增主要是「老人模式」排版与医疗/药店 POI 检索（`tools.py: search_pois_amap` 已可复用，需加类型）。

### 4.2 组织者决策包

群体出游真正的痛不是规划，是「选不出来」和「改一次要通知一遍」。付费者是那个最累的组织者，动机是「少吵架、少返工、别落埋怨」——情绪价值比效率好卖。

**商品**：多方案对比投票（带截止时间）+ 最终版一键分发（每人一份带自己分工）+ 变更实时通知 + 费用分摊。
**复用**：`collab_service`（share/edit token）、投票与评论、`ws_broadcast`（实时同步）、`expense_service`（payer 自由文本、append-only、未指定 payer 计入总额不参与分摊）。
**定价**：¥19.9/行程。

### 4.3 内容生产工具（B 端，留存最好）

卖给「输出行程的人」而不是「消费行程的人」：旅行博主、MCN、本地生活号、定制游工作室。他们每天要多条内容 / 多份行程，工具替代的是工时 → 付费意愿硬、留存高。

**复用**：`xhs-note` 生成（LLM 主路径 + 模板兜底，`source` 标注）、画廊发布与评分（`gallery_service` / `rating_service`）、导出图片、`note_import` / `link_import` / `screenshot_import` / `email_import`（攻略 → 结构化行程，敌意输入剥离）。
**定价**：¥199–499/月。

**延伸**：`escalation_service.py` 已留「人工复核队列」的口子（从 `plan_data.quality` 派生，不新增表）。这是「AI 出稿 + 真人精修」服务溢价（OTA 定制师模式的轻量版）的现成接口——卖服务比卖软件贵，且不需要新做系统。

### 4.4 行后回忆册

行程 + 照片 + 评论 + 投票 + 打卡事件 + 徽章（`passport_service` 7 条规则）+ 旅程进度投影（`journey_service`，读时聚合、`data_complete` 诚实标注）→ 可印刷的纪念册 / 年度旅行报告。

**为什么单价最高**：¥68–198 是「礼物/纪念品」心理账户，不是软件费。可对接在线印刷分成。

## 五、对已有方案的修订

### 5.1 修订 `c1-open-core-saas.md` §二 的付费墙表

| 原方案 | 修订建议 | 理由 |
|---|---|---|
| 「无限规划 + 优先级队列」为 Pro 核心 | **降级为顺手升级项**，不做主付费点 | 低频场景无感；且直接暴露 token 成本 |
| 「多人协作 Pro（人数/行程上限）」 | 保留，但改为**卖决策包**而非卖席位 | 卖「少吵架」比卖「多一个人」好卖 |
| 「高级导出（无品牌/高清）」 | 保留为**转化钩子**，不做收入来源 | 客单太低 |
| 「城市攻略数据包」 | 暂缓 | 内容型差异化需持续投入，ROI 不明 |
| 「旅行中助手」列为后续 | **升格为第一付费点** | 代码已建成 90%，且付费点长在托管运行上，避开 open-core 矛盾 |

### 5.2 与开源策略的关系

`c1` 硬伤二是「MIT 全开源 → 技术用户自己部署，永远不付费」。本报告的付费点按「是否可被自托管白嫖」重新分类：

| 付费点 | 自托管能否白嫖 | 结论 |
|---|---|---|
| 行中安心包 | ❌（需常驻服务 + 推送 + 多端） | **最适合做第一付费点** |
| 踩坑体检 | ✅（纯规则，可离线跑） | 适合做**转化钩子**（低价、走量） |
| 代做 / 送礼包 | ❌（本质是服务） | 适合高客单，与开源完全不冲突 |
| 组织者决策包 | ⚠️（需服务端广播） | 半适合 |
| 内容生产工具 | ✅ | B 端自托管者本来就不买 |

**结论**：付费点应优先选「依赖托管运行」或「本质是服务」的，而不是选「功能更强大」的。这一条比功能分层更重要。

## 六、落地优先级与 MVP 拆解

### P0：¥19.9 行中安心包（本周量级）

前置：支付（微信/支付宝，需主体与商户号）——**这是唯一硬阻塞**。

1. **entitlement 模型**：`TripEntitlement(trip_id, product, status, expires_at)`，一次迁移；校验点挂在 `live` / `revise` / `plan-b` 路由。
2. **商品页**：出行前 24h 触达（事件流已有 `record_event`，加一条 `product.offered`）。
3. **收银台**：单次购买，不做订阅、不绑卡、行程结束自动失效。
4. **移动端首屏**：`live_status` 已返回今日 day，前端做一个移动优先的「今日」页（打卡/跳过/顺延三个动作 + 天气 + 替代候选）。
5. **失败降级**：支付回调失败不阻断行程使用（沿用项目「降级不阻断」哲学），仅不写 entitlement。

### P1：踩坑体检（P0 之后 1–2 周）

## 七、共同缺口（诚实清单）

| 缺口 | 现状 | 影响 | 处理 |
|---|---|---|---|
| **支付 / 账单基建** | 全仓无 stripe / billing / subscription / payment 代码 | 阻塞所有付费点 | 需要主体 + 商户号；技术上最小实现 = 一次性订单表 + 回调 + entitlement |
| **真实价格与延误数据** | `discount_service` 只有规则库；无航班/高铁状态 | 省钱报告价值上限低；行中救急缺输入 | 联盟 API / 第三方延误服务，独立工程线 |
| **移动端行中体验** | 桌面 Web（Vue3 + Element Plus，非移动优先） | 行中付费发生在手机 | PWA 已有基础，需移动优先重排「今日」页 |
| **真实用户与流量** | 0 用户（`c1` 硬伤三） | 无转化率可测 | 仍应走「先内容/开源攒流量，再上付费墙」的顺序 |

**注意**：本报告不改变 `c1` 的启动顺序结论——**C1 不先于主线 A（内容 + 开源）启动**。付费点是「墙的图纸」，不是「现在就去砌墙」。

## 八、判定线与不做清单

### 判定线（写死，达不到就回主线 A）

| 信号 | 线 | 未达标动作 |
|---|---|---|
| 行中包开通率（出行前推送触达后） | ≥ 8% | 说明痛点不成立，回退到纯免费 |
| 踩坑报告 → 支付转化 | ≥ 5% | 说明报告不够吓人，重写结论呈现 |
| 「修掉」按钮点击率（已付费） | ≥ 50% | 说明卖的是好奇不是需求 |
| 行中功能使用率（打卡/顺延/跳过任一） | ≥ 30% | `c1` 硬伤一的判定线，未过则 Pro 定位回退到「次数 + 协作」 |
| 行程结束后 30 天复购 | ≥ 15% | 说明是一次性生意，考虑转服务（代做）而非产品 |

### 不做清单

- ❌ **首页订阅墙** / 注册即付费墙（低频产品最贵的错误）
- ❌ 把「AI 规划次数」作为首屏卖点（等于让用户算 token 账）
- ❌ 实时比价作为第一版收入来源（无价格数据，做了也是假的）
- ❌ 卖「多设备同步 / 离线」（PWA 已有，用户不会为此付费）
- ❌ 去水印 / 高清导出作为收入项（客单太低，只当转化钩子）
- ❌ 在没有任何真实用户前自建订阅体系（先攒量，再砌墙）
