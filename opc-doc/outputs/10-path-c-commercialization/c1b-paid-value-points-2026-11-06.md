# 付费点设计报告：让用户舍得花钱的七个点

> 日期：2026-11-06
> 承接：`c1-open-core-saas.md`（Pro 分层）· `path-c-research.md`（商业化全景）
> 性质：方案设计（未投入执行）。所有"已有能力"均经代码核对，附录 A 给出文件与行号。
> 一句话：**别卖"次数"，卖"这一次别出错"。**

---

## 一、摘要

### 1.1 核心判断

旅游是**低频、高价决策**（一趟 3k–30k），所以：

- 订阅制（¥19.9/月）在心理上是"我一年只用 3 次却月月扣钱" —— 结构性劣势；
- 一次性付费（¥9.9–69）锚定的是**行程总价的 0.1%–2%** —— 心理门槛极低。

付费意愿可以近似为：

```
付费意愿 ≈ (省下的钱 + 避免的损失 + 省下的心力) × 价值可见度 ÷ 支付时的摩擦
```

本报告所有付费点都按这个公式筛选，而不是按"功能多不多"。

### 1.2 七个付费点（按舍得程度排序）

| # | 付费点 | 谁掏钱 | 触发时机 | 建议定价 | 代码复用 | 新增工作量 | 优先级 |
|---|---|---|---|---|---|---|---|
| 1 | 行中救急包 | 出行者本人 | 行中出状况 / 行前 24h | ¥19.9–29.9 / 行程 | ★★★★★ | 中（移动端 + 支付） | **P0** |
| 2 | 踩坑体检报告 | 出行者本人 | 质检完成瞬间 | ¥9.9 / 次 | ★★★★★ | 低（几乎零） | **P0** |
| 3 | 省钱报告 | 出行者本人 | 定稿 / 导出前 | ¥9.9 / 次 | ★★★☆☆ | 中（需真价格源） | P2 |
| 4 | 代做 / 送礼包 | 子女、朋友（非出行者） | 下单即付 | ¥39–69 / 份 | ★★★★☆ | 中（老人模式排版） | P1 |
| 5 | 组织者决策包 | 同行组织者 | 多人出行前 | ¥19.9 / 行程 | ★★★★☆ | 低 | P1 |
| 6 | 内容生产工具 | 博主 / MCN / 定制师 | 月订阅 | ¥199–499 / 月 | ★★★★☆ | 中（批量 + 模板） | P2 |
| 7 | 行后回忆册 | 出行者本人 | 行程结束后 | ¥19.9 数字 / ¥68–198 实物 | ★★★★☆ | 中高（印刷对接） | P3 |

> 星级为"现有代码能否直接支撑"，不是价值判断。

### 1.3 最值得先做的一件事

把已完成的 **踩坑体检（纯规则、零 LLM 成本）+ 一键顺延（行中）+ 费用分摊** 打包成
**「¥19.9 行中安心包」**，在**出行前 24 小时**推送开通。

理由：代码 90% 已存在、边际成本接近零、踩在痛点峰值、一次性付费无订阅抵触。

## 二、方法论：三条判据

### 判据 1：价值必须可见（Value Visibility）

用户不为"我做了很多工作"付钱，为**能看见的结论**付钱。

- ❌ "多 Agent 协作规划" —— 用户看不见，也不关心；
- ✅ "你这趟有 4 个坑，第 2 天博物馆周一闭馆" —— 看得见，且立刻可验证；
- ✅ "本趟可省 ¥680" —— 可量化，直接对账。

### 判据 2：收费必须发生在痛点峰值（Moment-Based Paywall）

同一个功能，放在不同时机，转化率差一个量级：

| 时机 | 用户心理状态 | 适合卖 |
|---|---|---|
| 首页 | "我先看看这是什么" | ❌ 不要卖任何东西 |
| 质检报告弹出后 | "啊，原来我这趟有问题" | 体检报告 / 一键修复 |
| 出行前 24h | "明天就走了，别出岔子" | 行中安心包 |
| 行中出状况 | "现在怎么办？" | 救急（支付意愿最高） |
| 导出 / 分享前 | "要发给别人看了" | 精美版 / 去品牌 |
| 行程结束后 | "这趟挺值的" | 回忆册 / 故事卡 |

**结论：首页永远不卖订阅。** 低频产品的弱点（"我一年才用几次"）一旦被擺到首页，用户立刻算清账。

### 判据 3：支付摩擦要最小（Friction）

- 单次支付 > 订阅（无需解约心理）
- 按行程 / 按份 > 按月（跟使用周期对齐）
- 行前推送 > 站内常驻（借"即将出发"的紧迫感）

### 为什么"无限次规划"是伪付费点

- 一次完整规划的真实成本约 ¥0.05–0.15（`c1-open-core-saas.md` 已测算），用户一旦知道，会觉得 ¥19.9/月买"无限次"很荒谬；
- 低频场景下"无限次"价值接近零 —— 用户一年最多用 3–10 次；
- 它把竞争直接引向"更便宜的 token"，那是我们必输的战场。

**保留它作为"顺手升级"选项即可，不能当收入主力。**

## 三、七个付费点详解

### 3.1 【P0】行中救急包

**卖什么**
行程开始后：暴雨、景区临时闭园、高铁/航班延误、同伴体力不支、临时想改路线。
一键"今天来不及了"整体顺延、跳过某站、换附近替代、重排剩余天数。

**为什么舍得**
此刻用户的替代方案是「自己重排一遍 + 跟同行的人吵一架 + 白跑一趟」。
¥29.9 在这个时刻的心理价值远高于账单金额。

**已有能力（代码核对）**

| 能力 | 位置 |
|---|---|
| 行中今日视图 / 阶段推断 | `backend/app/services/live_service.py:49,64,80` |
| 打卡 / 跳过 / **一键顺延** | `live_service.py:157,218,275`（`delay_today` 复用 revise 原子内核 + DrivingGate） |
| 免登录同行者也能操作 | `live_service.py:174,232,297`（share/edit token） |
| 原子修订 + 回滚 | `services/revise_service.py`（`_apply_diff`） |
| 备选方案（零 LLM） | `services/plan_b.py:251` |
| 闭馆 / 节假日校验 | `services/dynamic_facts.py:154` |
| 体力负荷 | `services/time_validation.py:71`（`EXERTION_BY_TYPE`） |
| 自驾超限校验 | `services/driving_service.py:32-34` |
| 事件流 + PWA 通知 | `services/event_service.py` + 前端 `TripEventFeed.vue` |

**交付形态**
按行程售卖：`trip_id` 维度的权益（entitlement），出行前 24h 推送开通，行程结束后自动失效。
不绑定账号长期订阅 —— 用户不会觉得"被套住"。

**定价**：¥19.9（早鸟）/ ¥29.9（标准）
**边际成本**：行中约 3–5 次 LLM 修订 × ¥0.05–0.15 ≈ ¥0.3–0.7 → 毛利 > 95%

**缺口**
1. 移动端体验：当前是桌面 Web，而行中付费发生在手机上（最大工程项）；
2. 实时延误数据（航班/高铁状态）—— 第一版可以用"用户手动输入延误"降级，不阻塞；
3. 支付与权益校验中间件（见 §5）。

**验证信号**：行前推送触达后的开通率 ≥ 8–10%（自设判定线）；行中打开率 ≥ 30%。

---

### 3.2 【P0】踩坑体检报告（投入产出比最高）

**卖什么**
定稿后出一份「本趟风险体检」：

```
第 2 天（周一）· 省博物馆 —— 周一闭馆，建议改到第 3 天
第 3 天 · 单段驾车 180km，超出自驾上限（120km），当天过赶
第 4 天 · 体力累计 9.2 小时，含登山，实际耗时会明显上浮
第 5 天 · 国庆窗口，景区限流风险
跨城衔接 · 缓冲不足 40 分钟
```

**为什么舍得**
酒店、门票大多不可退。用户怕的不是花钱，是**白跑一趟**。
这是"保险心理"——比"效率工具"好卖得多，且不需要教育用户。

**已有能力**：几乎 100% 现成。
`dynamic_facts`（闭馆/免费日/节假日）+ `time_validation`（TimeGate + 体力）
+ `driving_service`（自驾门）+ `multi_city`（衔接缓冲）。**零 LLM 成本，毫秒级返回。**

**交付形态**
免费层给"发现 4 个风险"的摘要 + 每条一句话；付费 ¥9.9 解锁完整清单 + 修复建议 + 一键全修（走 revise diff）。

**定价**：¥9.9 / 次（或免费 1 次/月）
**边际成本**：0（纯规则）→ 毛利 ≈ 100%（仅支付手续费）

**为什么这是最好的第一个付费点**
- 零新开发：只差"包装成商品 + 支付入口 + 报告页"；
- 零边际成本：不烧 token；
- 位置极佳：天然长在质检报告下面（用户刚被告知"有问题"的瞬间）；
- 诚实：全部产出带 `basis=rule_based`，可解释、可申诉。

**验证信号**：质检页付费转化 ≥ 3–5%；退款率 < 5%（若高，说明报告有误报 → 优先修规则）。

### 3.3 【P2】省钱报告

**卖什么**
把预算、折扣规则、免票日、证件优惠、城市通票、套票算成一张"对账式"结论：
「本趟可省 ¥680」，逐项给"怎么省 + 去哪办"。

**为什么舍得**：省 680 收 9.9 —— 唯一不需要解释"为什么要付"的定价。

**已有能力**
- `services/budget_service.py`（预算明细/城市基准价）
- `services/discount_service.py`（确定性规则库：学生证/老年证/年卡/平台通用优惠，`confidence ≥ 0.8` 才输出）
- `services/servicing_service.py:117`（`build_discounts_view`，Tavily 搜索 + **无来源即丢弃**硬闸门）

**诚实口径的边界（重要）**

当前能卖的只有**规则级省钱**：证件优惠、免票日、年卡、通用平台券。
**卖不了实时比价**（某酒店今日价、某景区今日票）—— 那需要 OTA 联盟/分销 API，是另一条工程线。

**定价**：免费给"可省金额"摘要，¥9.9 解锁逐项方案。
**验证信号**：点击"查看怎么省"的比例 ≥ 15%；实际核销（用户回填"确实省到"）≥ 3%。

> 若接入真价格源，这个点可以升级为"比价 + 代订返佣"，商业价值量级完全不同；但**不要把它放进第一版**。

---

### 3.4 【P1】代做 / 送礼包（孝心溢价，几乎无人做）

**卖什么**
子女给父母、朋友给朋友做一份"安心行程"：¥39–69/份。

差异化不在行程本身，在**适老化 + 远程安心**：
- 大字版、每天最多 2 站、少走路
- 附近医院 / 药店 / 派出所
- 紧急联系人、酒店前台电话
- 一键导航、语音播报
- 入住指引（`checkin_service`：模板基座 + LLM 润色，且**明确不收集证件号**）

**为什么强**
1. **付费人与使用人分离** → 价格不敏感（送礼不会因为 39 块犹豫）；
2. 买的是"我不在旁边也放心" —— 情绪价值，比效率好卖；
3. 天然裂变：收礼的人会问"这谁做的"。

**已有能力**：导出 PDF/图片（`jspdf` + `html2canvas`）、打包清单、体力负荷提示、入住指引、免登录分享链接（`share_token`，无需注册即可打开）。
缺的只是**适老化排版模板**和"附近医疗/药店"检索。

**定价**：¥39（基础）/ ¥69（含亲情语音版 + 打印邮寄）
**验证信号**：礼物场景下单占比 ≥ 10%；收礼方二次使用（自己再规划一趟）≥ 20%。

### 3.5 【P1】组织者决策包

**卖什么**
8 人出游真正的痛不是"排不出来"，是「**选不出来**」和「**改一次要通知一遍**」。

- 多方案对比投票（带截止时间，到期自动锁定）
- 最终版一键分发，每人一份带自己分工的版本
- 变更实时通知（已投票者收到）
- 行中费用分摊（谁欠谁）

**为什么舍得**：付费者是"组织者"——那个最累、最容易落埋怨的人。他买的不是软件，是**少吵架、少返工**。

**已有能力**：评论 + 👍/👎 投票（`trips_share.py:124,137`）、`edit_token` 受邀编辑、WS 实时同步（`/ws/trips/{id}/collab`）、`expense_service`（分摊，payer 为空串则计入总额但不参与分摊 —— 诚实口径）。

**定价**：¥19.9 / 行程 或 组织者年费 ¥49
**缺口**：投票"截止 + 锁定 + 结果裁决"这套状态机（低工作量）。
**验证信号**：多人行程（≥3 人）中付费占比；组织者复购（一年内第二次出行）。

---

### 3.6 【P2】内容生产工具（B 端，留存最好）

**卖什么**
不卖给游客，卖给**"输出行程的人"**：旅行博主、MCN、定制师、本地生活号。

- 攻略链接 / 截图 / 邮件 → 结构化行程（`note_import` / `screenshot_import` / `email_import` / `social_import`）
- 一键多平台出稿：小红书 / 朋友圈 / 长图海报（`story_service.py`，三渠道模板 + LLM 主路径 & 模板兜底 + PII 过滤）
- 批量出图、可发布行程页（画廊 `publish` + `clone`）
- 定制师场景：`escalation_service`（人工复核队列）天然支持「AI 出稿 + 真人精修」的服务溢价

**为什么付费意愿硬**：它替代的是**工时**，不是替代"灵感"。博主一天要出多条内容，工具直接换算成时间。

**定价**：¥199 / 月（个人）/ ¥499 / 月（团队，含 5 席）
**验证信号**：周活 ≥ 3 天；单账号月产出 ≥ 10 条行程/内容；月流失率 < 8%。

### 3.7 【P3】行后回忆册

**卖什么**
行程 + 照片 + 评论 + 投票 + 打卡事件 + 徽章（`passport_service`，7 个初始徽章）
+ 地图轨迹 → 可印刷的旅行纪念册 / 年度旅行报告。

**为什么**：¥68–198 是**实物/礼物**支出，不是软件费，心理账户完全不同。
「印出来」的付费意愿远高于「订阅一个 App」。

**已有能力**：`journey_service`（行中事件投影 + 高光）、`passport_service`（徽章）、`story_service`（故事卡）、导出（JSON/图片）。
缺：印刷供应商对接（世纪开元 / 咕咕机类）、版式设计、物流。

**定价**：¥19.9 数字版 / 实物 ¥68 起（与印刷方分成）
**验证信号**：行程结束后 7 天内生成率 ≥ 10%；数字版 → 实物升级率 ≥ 15%。

## 四、收入结构：不是七个点，是四类钱

单看每个点都不大，组合起来才是可持续的结构：

| 类别 | 来源 | 特征 |
|---|---|---|
| **C 端一次性** | 体检报告、行中包、省钱包、决策包 | 无订阅抵触，随行程自然发生 |
| **他人代付** | 送礼包 | 付费人与使用人分离，价格不敏感 |
| **B 端订阅** | 内容生产工具 | 留存最好、替代工时、可涨价 |
| **交易分成** | 回忆册印刷、未来 OTA 返佣 | 不向用户收费也能赚钱 |

一人公司的现实选择：**先做 C 端一次性（验证付费意愿）→ 再做 B 端订阅（稳定现金流）→ 交易分成最后做（需要供应链）。**

## 五、支付与计费基建（唯一的前置硬依赖）

全仓库当前**没有任何 payment / billing / subscription 代码**（已核对 `backend/app/` 全量搜索无结果）。这是所有方案的共同前置。

### 5.1 最小可用设计（不要一步做成订阅系统）

三张表足够：

| 表 | 字段 | 说明 |
|---|---|---|
| `products` | code, name, price_cents, currency, kind(one_off/subscription), entitlement_spec | 商品定义（配置化，不写死） |
| `orders` | id, user_id, product_code, amount, status(created/paid/refunded), channel, out_trade_no, paid_at | 订单 |
| `entitlements` | id, user_id, product_code, scope(trip_id/account), expires_at | 权益（行中包挂 trip_id） |

`entitlements` 是核心抽象：**所有付费点都统一成"某个 scope 上的一段有效期"**，
未来加功能不改表结构，只加 `entitlement_spec`。

### 5.2 支付渠道

- 微信 Native / JSAPI + 支付宝当面付：需要**主体 + 商户号**（个体户/公司均可）；
- 过渡方案：知识付费平台/小店挂单 + 手动发码（能验证意愿，不能规模化）；
- **务必先确认主体资质**，这是唯一可能卡住整条路线的事。

### 5.3 权益校验

一个 FastAPI 依赖 `require_entitlement(scope="trip", code=...)`，读 `entitlements` 判过期。
不要在每个业务函数里散落 `if paid` 判断 —— 集中在一层，方便灰度与退款。

## 七、风险与不做清单

### 7.1 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 支付合规 | 个人主体无法开商户号 | 提前确认资质；过渡用平台代收 |
| 责任边界 | 体检报告漏判导致白跑，用户投诉 | 全部标注 `basis=rule_based` + "以现场为准"免责；不承诺"保证不出错" |
| 数据准确性 | 延误/闭园信息错误 | 第一版不接实时数据，用"用户手动输入"；绝不伪造"可订/可去" |
| 退款与发票 | 一次性数字商品退款政策 | 明确"行程开始前可退"，降低纠纷 |
| 低频绝对值 | 即使转化好，C 端天花板仍低 | 必须并行 B 端（§3.6），不能只靠 C 端 |
| 支付摩擦 | 微信/支付宝跳出体验差 | 行前推送 + 一键拉起；不做站内钱包 |

### 7.2 不做清单（沿用既有裁决）

- ❌ 首页卖订阅
- ❌ 把"无限次规划"当收入主力
- ❌ 去水印 / 高清导出单独卖（客单太低，只作转化钩子）
- ❌ 实时比价（没有供应链前不碰，避免"假装可比价"）
- ❌ 企业差旅 TMC（`path-c-segments-content-tmc-events.md` 已裁决：重资产必死）
- ❌ 免费为 B 端定制换案例（定制项目坟场红线）

## 八、结论

1. **低频不是不能收费，是不能按"次数"收费。** 按行程、按份、按峰值时刻收费，转化逻辑完全不同。
2. **最高投入产出比的付费点是"踩坑体检"**：代码已 100% 存在、零 LLM 成本、长在用户最焦虑的那一秒。
3. **最舍得付费的时刻是"行中出状况"**，而这块的核心代码（顺延/跳过/原子修订）已经写完 —— 缺的只是移动端和支付。
4. **真正的收入结构是四类钱的组合**：C 端一次性 + 他人代付 + B 端订阅 + 交易分成。
5. **唯一硬前置是支付基建**，其余都是包装与排版。
