## 1. 背景（Problem Statement）

**FloatTrip（途见）** 主打"**一句旅行想法 → 可继续修改的逐日行程**"，技术栈 FastAPI + LangGraph + OR-Tools CP-SAT + React，核心卖点是：

- 对话式 **Planning Brief**：先聊清楚再规划，缺信息时用补充卡片继续；
- **确定性优化器**（CP-SAT）做选点/排序/排程，而不是让 LLM 一次性写时间表；
- **旅行长期记忆**（可查看/编辑/忘记，本次需求优先于历史画像）；
- **@ 引用已有行程修改** + Planner/Reviewer 修改循环；
- **拖拽编辑、跨日切换、撤销/重做**，保存时服务端重算距离；
- **持久化 Agent Runtime**（排队/SSE 回放/取消/重试/等待补充）；
- 独立 **React Native 移动端**。

**现状（我方实查）**：我们已具备多 Agent 单一职责编排（Collect 六路并行 + 质检闭环 + diff 修订）、真实数据（高德/降级链）、预算/协作/记账/旅程追踪/护照徽章/故事卡、预订打通（outlink + 回填）、易分享、i18n 双语言、T-A-O 轨迹。**规划深度与闭环丰富度我们是领先的。**

**本次要回补的差距**（FloatTrip 有、我们相对弱）：
1. **确定性行程求解**：我们靠 Planner/质检重生成，缺"LLM 候选 + 确定性优化器排程"的可靠性；
2. **旅行长期记忆的产品化**：我们有 profile 表，但缺"用户可见、可编辑、可忘记"的管理界面与对话内注入；
3. **@ 引用已有行程修改**：我们能改行程，但从对话里"明确 @ 选择修改对象"的产品形态不足；
4. **拖拽编辑 + 撤销/重做 + 跨日调整**：我们编辑是表单式，缺直接操作体验；
5. **Agent 任务运行时**：有 task 查询，但排队/取消/等待补充/断线回放不完整；
6. **移动端占位**：无 App。

（注：CP-SAT 求解器自己实现门槛高；本轮把"确定性求解"定位为 **P1 实验**，先落"候选 + 规则排序 + 硬约束校验"，把 OR-Tools 真正落地放到有数据验证后。）

## 3. Scope

### 3.1 In Scope（本轮迭代做）

- **P1 — 行程编辑体验**：拖拽换序 + 时段调整 + 撤销/重做 + 跨日编辑；保存时服务端重算距离/预算。
- **P1 — 旅行记忆管理**：画像偏好条目列表、可新增/编辑/忘记；对话内注入"本次需求优先于历史画像"。
- **P1 — @ 引用行程修改**：对话输入框 @ 选择已保存行程；明确当前修订对象；保留原行程版本。
- **P1 — 确定性行程求解**：候选生成后走"规则排序 + 时间/距离硬约束校验 + 失败修复"（先规则、后 CP-SAT 实验）。
- **P2 — Agent 任务运行时增强**：排队、取消、重试、等待补充、SSE 断线回放。
- **P2 — 移动端占位 / 响应式加固**：最小 React Native 壳 + 后端复用；桌面优先不改。

### 3.2 Out of Scope（明确不做）

- 不实现完整 OR-Tools CP-SAT 求解器（先规则，求解器留作实验变体）。
- 不做多语言扩展（维持 zh/en）。
- 不做推送、不做社交 Feed、不做支付/清算（沿用已有边界）。
- 不做移动端全面功能（只做最小可用壳，复用后端）。

## 4. User Personas & Stories

**Primary Persona（小刘）**：预算敏感城市白领，重视真实信息与行程可调整性，旅行中随手记录、回来发朋友圈。
**Secondary Persona（同行旅伴）**：拿到分享链接，免登录评论/投票/打卡，想回看"我们这次一起做了什么"。

### Story 1（行程直接编辑：拖拽 + 撤销）
作为旅行者，我想要在行程详情里直接拖拽换序、调整时段，并且能撤销/重做，以便不改对话也能把行程改顺。

**Acceptance Criteria:**
- [ ] 逐日 stops 支持拖拽换序（同日内/跨日）、开始/结束时间调整、地点更换
- [ ] 编辑以草稿形式保存：撤销/重做覆盖顺序、时间、地点变更；未保存退出不落库
- [ ] 保存时服务端重算每段距离与预算（复用 budget 校准），失败回滚不产生半保存
- [ ] i18n zh/en 键齐全；后端测试 ≥ 8 例（重算/撤销契约/跨日/失败回滚）

### Story 2（旅行记忆管理）
作为旅行者，我想要在"旅行偏好"里看到系统记住我的偏好条目，并且可以编辑、忘记或补充，以便不用每次重新解释。

**Acceptance Criteria:**
- [ ] `GET /api/v1/profile/preferences` 返回可读条目列表（条目含来源、更新时间）
- [ ] 前端画像页：支持新增、编辑、删除（忘记）偏好条目；删除后规划上下文不再注入
- [ ] 规划时注入"本次明确需求优先于历史画像"的提示；同一主题本次需求覆盖历史
- [ ] 后端测试 ≥ 6 例（CRUD/优先级/删除后不注入）

### Story 3（@ 引用行程修改）
作为旅行者，我想要在对话里用 `@` 选择某个已保存行程，明确"我要改这个"，以便对历史行程直接发起修订而不是开新计划。

**Acceptance Criteria:**
- [ ] 对话输入框 `@` 弹出已保存行程选择器；选中后作为本次对话的修订对象
- [ ] 后端接收修订对象 trip_id，走 PlanReviseAgent diff 原子修订（复用既有 revise 链路）
- [ ] 修订产生新版本行程（保留原版本），对话完成后可跳转到新版本详情
- [ ] 后端测试 ≥ 6 例（@解析/权限/版本保留）

### Story 4（确定性行程求解）
作为旅行者，我想要规划结果"不是模型凭空排的"，而是经过可核对的地点筛选与时间/距离约束校验，以便减少"排得太满/顺序不合理"。

**Acceptance Criteria:**
- [ ] 规划流水线新增"候选排序 + 硬约束校验"步骤：同城 POI 按距离/评分排序，超时/超距的 stop 标记并尝试修复
- [ ] 校验失败走有限次修复 + 兜底（不成功则明确报错，不静默当成功）
- [ ] 保存行程时携带 `solver_meta`（排序依据/校验结果），前端可查看依据
- [ ] 后端测试 ≥ 8 例（硬约束/修复/兜底/依据字段）
- [ ] OR-Tools CP-SAT 作为 P1 实验变体，不阻塞本轮

### Story 5（Agent 任务运行时增强，P2）
作为开发者/用户，我想要规划任务可排队、可取消、可重试，断线后能回放进度，以便长任务不丢失、可控制。

**Acceptance Criteria:**
- [ ] `POST /planner/tasks` 支持排队（并发上限内排队）；`DELETE /planner/tasks/{id}` 支持取消
- [ ] 失败任务支持重试（复用幂等键，不产生重复行程）
- [ ] SSE 断线后可通过 `GET /planner/tasks/{id}/events?after=` 回放事件
- [ ] 后端测试 ≥ 8 例（排队/取消/重试幂等/回放）

## 8. 非目标与风险

- **非目标**：不做完整 CP-SAT（先规则）；不做多语言扩展；不做推送/社交；不做移动端全面功能。
- **风险**：
  - 拖拽编辑（Story 1）涉及前端状态复杂，可能拖版本；P1 内先做单日拖拽 + 撤销，跨日延后。
  - 确定性求解（Story 4）若规则排序质量不如 LLM，保留开关（feature flag）允许退回旧路径。
  - @ 引用（Story 3）需防越权：只允许本人行程；分享行程只读。
  - 任务运行时（Story 5）排队/取消引入并发与幂等复杂度，需严格测试。
