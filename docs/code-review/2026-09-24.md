# 代码审查报告：my-trip-planner（2026-09-24）

> 审查范围：后端 `backend/`（约 8.9k 行 Python）+ 前端 `frontend/src/`（约 3.9k 行 JS/Vue）+ 部署配置与测试。
> 验证方式：实际运行测试套件，**95 passed in 19.85s**（真实执行，无网络无 token）。

## 总体评价

工程质量明显高于平均水平的 AI Agent 应用：多 Agent 编排（`asyncio.gather` 并行采集 + Planner 整合 + Critic 质检闭环）、LLM 输出强校验、重试/熔断/降级三层容错、FakeLLM 测试替身、owner 隔离、原子修订——设计哲学（LLM 只做理解，代码做执行）贯穿始终，README 的诚实清单在业界难得。代码可读性好，注释质量高，异常体系统一。

发现 **2 个必须修复的严重缺陷**（含 1 个致 Google 登录线上必失败的 bug 和 1 个越权删除漏洞），以及若干值得注意的中级问题。

## 🔴 阻塞项（必须修复）

### 1. Google 登录 audience 取到字符而非 Client ID —— 线上必失败

**位置：** `backend/app/services/google_auth.py:33-38` + `:100`

```python
def _google_credentials() -> tuple[str, str]:
    client_id = settings.GOOGLE_CLIENT_ID
    if not client_id:
        raise GoogleAuthError(...)
    return client_id            # ← 声明返回 tuple，实际返回单个 str！
...
client_id = _google_credentials()[0]   # ← 对 str 取 [0] = 第一个字符
```

**原因：** `[0]` 取到的是 `GOOGLE_CLIENT_ID` 的**第一个字符**（如 `"4"`），传给 `verify_oauth2_token(audience="4")` 后，真实 token 的 `aud`（完整 Client ID）必然不匹配 → 校验必抛异常 → **只要配置了 Google 登录就永远 401**。

**为什么测试没抓到：** `tests/test_google_auth.py` 用 monkeypatch 替换了 `verify_oauth2_token` 直接返回 payload，绕过 audience 校验，掩盖了 bug。

**建议：**
```python
def _google_credentials() -> str:   # 改签名
    ...
    return client_id
# 调用处：
client_id = _google_credentials()
```

### 2. `delete_day` / `delete_stop` 缺少 owner 归属校验 —— 越权删除（IDOR）

**位置：** `backend/app/services/trip_service.py:140-155`

```python
async def delete_day(db, day_id, *, owner=None):
    day = await db.get(TripDay, day_id)      # ← 没校验所属行程归属
    ...
async def delete_stop(db, stop_id, *, owner=None):
    stop = await db.get(Stop, stop_id)       # ← 同样缺失
```

**原因：** 同文件 `update_stop` / `reorder_stops` 都先调 `_load_day_for_owner` 校验归属，唯独两个 delete 直接 `db.get` 裸查。**任何登录用户只要猜到/枚举 day_id / stop_id（UUID 但可经分享接口等途径获得）就能删除他人的日程/站点**，破坏 owner 隔离语义（README 明确宣称"行程与任务按用户隔离"）。

**验证：** `tests/test_api.py` 的 `test_owner_isolation` 只覆盖了 list/get 的 404，**没有覆盖 delete 越权**，所以漏洞未被发现。

**建议：**
```python
async def delete_day(db, day_id, *, owner=None):
    day = await _load_day_for_owner(db, day_id, owner=owner)
    await db.delete(day)
    ...
# delete_stop 同理（先校验 day 归属，再删 stop）
```
并补两条越权删除测试。

## 🟡 建议项（应该修复）

### 3. TripMap popup 拼接 HTML —— 存储型 XSS 面
**位置：** `frontend/src/components/TripMap.vue:48-52`
`m.name` / `m.description` 直接插进 popup HTML。数据来源包括 **LLM 输出**（可被提示注入诱导）和**受邀编辑**（任何人拿到 edit_token 即可写 `name`/`description`）。受邀者写入 `<img src=x onerror=...>`，owner 打开详情页即触发，且可窃取 localStorage 里的 JWT。修复：用 `document.createElement` + `textContent`，或复用依赖里已有的 DOMPurify。

### 4. `AGENT_MAX_ITERATIONS` / `TASK_EXECUTION_TIMEOUT` / `TASK_STALE_RUNNING_SECONDS` 是死配置
**位置：** `config.py:88-101`。全仓库搜索三者除定义处外**零引用**。文件注释说"超时标记 failed_timeout，避免卡死 worker 队列""启动恢复扫描：running 超时视为崩溃遗留"——这些能力**根本没实现**。worker 崩了任务永远卡在 running。要么实现，要么删配置并更新文档（deploy/README 已诚实写"任务队列在内存"）。

### 5. `available_provider_chain()` 是死代码 + `ENABLE_PROVIDER_FALLBACK` 未接线
**位置：** `providers.py:102,173`。README 声称"主 provider 失败后自动切换兜底 provider"，但 `invoke_with_resilience` 的 `chain = providers or [provider]`，而**没有任何调用方传 providers** → 兜底链从未生效，多 provider 只是"第一个能用的"。要么接上，要么改文档。

### 6. `graph.py`（LangGraph StateGraph）是死代码，langgraph 依赖白背
`backend/app/agent/graph.py` 332 行的完整 LangGraph 实现（`build_agent_graph`/`run_agent`）**全仓库无调用方**，实际编排是 `agents.py` 手写 asyncio。README 技术栈却列了 LangGraph。建议删除或说明定位，否则维护者会困惑"哪套是真相"。

### 7. 迁移链有假 revision 且 `has_table` 双轨 —— schema drift 炸弹
`alembic/versions/a1f2b3c4d5e6_add_user_profiles.py` 用了假 revision id，且 upgrade 里 `if not sa.inspect(...).has_table("user_profiles")` 才建表——若 dev 用 `create_all` 先建了表，该 revision 会被幂等跳过但**永远不记录**，未来对该表的增量迁移会缺基线。生产 `ENV=prod` 走 alembic、dev 走 create_all 的双轨长期必然漂移。建议：dev 也统一走 alembic，删掉 has_table 条件。

### 8. Nominatim 并发违反限速条款
`tools.py:284` `Semaphore(6)` 并发调 geocode，而 `geocode` 只在查询失败路径 `sleep(1.1)`——成功路径无节流。Nominatim 明令 1 req/s，会被封 IP。建议 geocode 前统一 `asyncio.sleep(1.1)` 或改串行。

### 9. 手动 API 的坐标无范围校验
`schemas/__init__.py:20-21` `StopIn.lat/lng` 无 `ge/le`（Agent 的 `StopSchema` 有）。可写入 `lat=999` 污染地图。补 `ge=-90,le=90` 等。

### 10. `generate_days_for_range` 无天数上限
API 接受任意 start/end，一次可插入几年（1825+ 天）。`PlanSchema` 限了 31 天，这里没限。建议上限 ~31 天。

### 11. `health` 在 DB 挂时返回 500 而非 degraded
`get_session` 依赖在 handler 之前解析，`db.execute` 前的连接失败会抛 500。健康检查应吞掉并返回 `degraded`。建议用独立连接或捕获更早。

### 12. 前端 `defaultDates()` 时区 bug
`PlanWizard.vue:66` `new Date().toISOString().slice(0,10)` 是 UTC 日期。UTC+8 晚间 20:00 后，本地已过午夜但 UTC 未过 → 默认出发日期变成**昨天**。应手写本地日期格式化。

### 13. 注册并发唯一约束竞态
`auth_service.py:66-70` 先查后插，两个并发注册同邮箱会撞 unique 约束 → IntegrityError 500 而非 400。捕获 IntegrityError 转 400 更稳。

## 💭 小改进（锦上添花）

- **重复代码：** `_normalize_trace` 在 `planning_service.py` 和 `revise_service.py` 各一份；`_TRIP_LOADS` 同样重复。可提取公共模块。
- **attraction/hotel agent 多 tool_calls 只取最后一个 ToolMessage**（`agents.py:354`）：LLM 一次生成多次工具调用时只保留最后结果。建议显式限定"只生成 1 个 tool_call"或遍历合并。
- **`VoteIn.value` 允许 0**（`collab.py:37`）：注释是 1/-1，但 schema 是 `ge=-1,le=1`，0 会被当有效票。用 `Literal[-1, 1]`。
- **`critic_agent` 的 plan 截断 6000 字符**：长行程会被截断评审失真。可分段或摘要。
- **`TripDetailView.diffText` 里 reorder index 显示**：`(a.index ?? 0) + 1`，后端 index 是 1-based，前端又 +1 显示，会显示"移至第 N+1 位"。核对一下（`revise_service._describe_actions` 原样透传 index）。
- **api/index.js 401 用 `window.location.href` 整页跳转**：SPA 里用 router 更平滑。
- **localStorage 存 JWT + XSS 面（#3）组合**：修复 #3 前建议至少把 token 放 httpOnly cookie。
- **`health` 数据库连接超时**：无显式 timeout，DB 假死时可能挂住请求。

## ✅ 值得肯定的部分

- **`revise_service._apply_diff` 的"预检全部动作 → 再原子执行"**模式非常扎实：LLM 只产 diff，代码校验目标/类型/位置，任一失败整体回滚，杜绝半生效状态。
- **DrivingGate 确定性校验**（`driving_service.py`）把自驾约束做成纯函数 + 单测，不依赖 LLM，构思清晰。
- **`invoke_with_resilience` 的重试+熔断+观测元数据（latency/token/cost）**设计完整，`_extract_observation` 甚至核算了美元成本。
- **Critic 降级放行、天气纯工具化、预算代码校准**——"LLM 只做擅长的事"贯彻得很彻底。
- **测试质量高：** FakeLLM 替身覆盖全链路，95 个测试 20 秒跑完、零网络零 token；conftest 用独立测试库 + TRUNCATE，隔离干净。
- **容错细节讲究：** `_validation_error_handler` 处理了 Pydantic ctx 里不可序列化对象的边界；`_parse_date` 宽容解析；lifespan 正确管理执行器生命周期。
