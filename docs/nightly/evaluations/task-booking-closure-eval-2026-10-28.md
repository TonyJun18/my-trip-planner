# task-booking-closure-eval 评估记录（2026-10-28）

**结论**: 三路线评估 + 短期选 A（outlink），经用户批准落地（task-booking-outlink 已实现），**本项关单**。

---

## 1. 问题

「规划→执行」断点：行程漂亮但用户仍要自己去比价下单。是否接入分销 API 打通预订闭环？

## 2. 供应商 / 数据源矩阵

| 路线 | 能力 | 成本 | 合规 | 小团队可行性 |
|---|---|---|---|---|
| **A. OTA 联盟跳转（outlink）** | 生成可点击预订外链（携程/去哪儿/12306 deep-link），用户跳出完成交易 | 极低（纯规则 + URL 组装） | 无支付牌照/资金池；跳转即用户自助交易 | ✅ 1 sprint，零资质 |
| **B. 浏览器会话式预订助手** | 对话内"搜索→比价→引导支付→凭证回填"（复用 ChatView AgentLoop） | 中（会话恢复/反爬/OTA 登录态风控） | 支付仍在浏览器，无资金接触 | ⚠ 可并行评估，风险高 |
| **C. 官方开放平台 / 分销 API 直连** | 携程开放平台 / 飞猪商家 / 同程分销：实时价/库存/下单回调 | 高（企业资质、审批以月计、签名机、对账沙箱） | 需商户入驻 + 佣金 CPS 协议 | ❌ 资本密集型，需真实用户规模 |

## 3. 定位分析

- 仓库既有文章（docs/articles/06、10）已论证：**预订层是库存+支付+合规的资本壁垒**（Mindtrip×Sabre×PayPal、Expedia×Layla）；
- 独立工具正解是把规划层做深（可修订/可验证/可协作/输入自由/可自托管），预订层不该小团队自建；
- A 路线恰好是「规划层 → 预订层」的最短低风险桥：不拥有交易，只做"触达真实交易"的引导 + 凭证回填，保持无库存、无资金、无合规。

## 4. 结论与落地

- **结论一（采纳）**：接入最小「酒店/车票比价跳转」类（A outlink）——`_deeplink` 纯函数 + `plan.bookings` 建议 + `TripBooking` 凭证回填 + `booking.*` 事件；
- **结论二（排队）**：B 会话式（中期形态，需真实余票源）与 C 分销 API（有真实用户规模再立项）列入 SRS §6 P2 观察。
