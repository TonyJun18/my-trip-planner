## 3. 差距 → 行动项（我们可补的差距 / 可借鉴的亮点）

1. **【补功能】全行程「预订前瞻扫描」**（Passage AI「Need tickets?」是 2026 市场上唯一的行中预订管理差异化——扫描全行程、标记 ≤12 个值得提前预订的站点、理由+链接、**确认号回填到站点**）。我们 10-28 已完成 booking outlink（TripBooking 状态机 suggested→…→confirmed），但**只在行程生成时产出建议，没有「对现有行程扫描值得提前订」的独立动作**，行中改版/新增站点后无提醒；确认号也只挂在 booking 表、未回填到 stop 级。这是「规划→执行」断点的最后一块砖：最小版（零凭证）= 规则库扫描（timed-entry/热门类目表，复用 booking 链路）+ POST /trips/{id}/bookings/scan 返回可订建议 + 确认号可回填 stop（复用 TripBooking reference 或 stop 挂 booking_id）+ 测试覆盖。与 10-28 方案 A 定位一致（仍不碰钱/库存/合规）。
   → 行动项 slug：**task-book-ahead-scan**
2. **【评估候选】餐饮时段锚定 + 站间步行时长**（Passage AI 步行导向核心——餐饮放进合理时段、站间步行分钟数、一键重排缩短步行；「步行城市」细分在 2026 评测热度高）。我们 time_validation 有类目营业基准/体力系数，但**无餐饮窗口锚定、无站间步行时长**。评估：①MEAL_WINDOWS 规则（早餐 7-10 / 午餐 11:30-14 / 晚餐 17-21，把同类餐饮候选锚定到合理时段，纯规则零凭证）；②站间步行估算（零凭证：城市中心 POI 间 5-15 分钟规则估算 vs 高德距离 API 需凭证——大概率后者关单，与 open-hours-real 同构）；可行则最小版先做餐饮锚定（排程校验 warning + 建议），步行时长评估后再说；不可行记降级关单。
   → 行动项 slug：**task-meal-walk-anchors-eval**
3. **【观察项·不入夜间队列】免费 AI 帮助限额 + 巨头预订扩张**：Wanderlog 免费 5 条/行程封顶 → 我们登录用户无限次 LLM 规划仍是成本敞口（10-15 guest-trial 已防匿名滥用，但**登录用户无额度治理**）；建议白天评估「高频用户限流/额度提示」（需用户立项，含配额表与计费模型，与 guest-trial 重启同源）。另 Google AI Mode 8-27 美国酒店预订 = 14 文《巨头免费化之后》最新增量素材（内容沉淀候选，视窗口另立，不占本夜）。
