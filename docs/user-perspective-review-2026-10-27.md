# my-trip-planner 用户视角梳理（产品定位 · 痛点 · 短板）

> 梳理基准：main 分支 @ 8e07e07（2026-10-27，前端 social 五通道接线后）
> 事实来源：仓库代码取证（README 32 项功能 / LandingPage 文案 / screenshot_import 平台依赖 / night-build-todo 待办状态 / 10-21 项目复盘 / 10-27 代码质检）
> 视角声明：本文全部从「普通用户」（非工程师）视角出发。凡结论分两类——「代码实证」（仓库里能查到实现）与「体验推断」（依据定位与行业常识的合理推断，标注 ⚠️）。

## 一、这个产品是什么：一句话

**免费、开源的 AI 行程规划工具**：用户说一句「杭州 3 天 2 晚，5000 预算，带爸妈」，背后 4 个 AI 专家 Agent（景点 / 天气 / 酒店 / 规划）并行协作，产出一份**可执行、可修改、可分享、可导出**的行程；规划完不算完——行中还能打卡、顺延、记账。

自我定位是**「规划层」而非「预订层」**：不替用户花钱订票，而是把「行程方案」这件事做到深——**可信（质检）、改得动（修订一等公民）、能协作（分享/投票/编辑权）、数据自由（导出/自托管）**。

## 二、想服务谁：目标用户与匹配度

| 用户群 | 典型场景 | 匹配度 | 说明 |
|---|---|---|---|
| 自由行小白 | 第一次去某地，不知道玩什么、怎么排，怕踩坑 | ✅ 核心 | AI 规划 + 四维质检正好接住「不敢信 AI」的信任缺口 |
| 结伴出行小组 | 3-5 人、异地同伴，要一起商量行程 | ✅ 差异化 | 分享/投票/受邀编辑/WS 实时同步是全场最完整的协作组合 |
| 攻略收藏爱好者 | 小红书刷到攻略，截图/链接/文本一堆 | ✅ 强 | 四通道导入（截图 OCR / 社交文本 / 链接 / 预订邮件） |
| 行程洁癖自由行老手 | AI 生成后必须手动微调每一点 | ✅ 强 | 对话修订 / 地图拖拽 / 行内编辑 / 整日重排并存 |
| 数据主权敏感用户 | 平台倒了行程就没了（Tripnotes 前车之鉴） | ✅ 差异化 | JSON 导出 / 打印 PDF / MIT 开源 / 可自托管 |
| 希望「一句话包办到订票」的用户 | 只想少干活，行程+酒店+票一步到位 | ⚠️ 不匹配 | 明确不做预订闭环（见短板 #1） |

## 三、用户旅程 × 痛点 → 解法全景

### 1. 规划前——「不知道去哪、不知道怎么开始」

| 用户痛点 | 解法（代码实证） |
|---|---|
| 打开 App 面对空表单，第一屏劝退 | 灵感入口（预算/兴趣/季节 → 推荐目的地卡片，规则库 23 目的地） |
| 目的地明确但懒得填十几项 | 城市模板深链预填（gallery city-templates） |
| 攻略散落各处，手动抄进 App 太蠢 | 四通道导入：小红书截图 OCR / 社交分享文本 / 攻略链接 / 预订邮件 → 结构化站点候选 |
| 说不出自己有什么偏好 | 主动提问 Q&A（人群/节奏/避峰）+ 可跳过的 questions 追问 |

### 2. 规划中——「AI 行程看着漂亮，但我不敢信、也改不动」

| 用户痛点 | 解法（代码实证） |
|---|---|
| AI 推荐闭馆景点、同一天排 120km、预算瞎估 | 四维质检闭环（Critic 打分 <80 带问题重生成）+ 确定性规则门：DrivingGate（单段 120km/150min、单日 300km）、TimeGate（闭馆 30min 缓冲、单日 ≤5 站/≤480min）、体力负荷、动态事实（周一闭馆等特例表） |
| AI 行程是死的，改一处全乱 | 对话式修订（AI 出 diff + 代码原子执行 + 整体回滚）+ 地图拖拽 + 行内 PATCH + 整日重排 |
| 千篇一律模板行程 | 主动提问并入规划上下文 + 跨会话用户画像自动注入 |
| 只有一套方案不放心 | 确定性 Plan B 规则引擎备选方案对照 |

### 3. 规划后——「行程要给同伴看、一起商量」

| 用户痛点 | 解法（代码实证） |
|---|---|
| 行程散在聊天记录，同伴各看各的 | 免登录分享链接（幂等复用，含预算汇总） |
| 大家意见不一没法协商 | 评论 + 每日站点 👍/👎 投票，≥50% 成员一致即「小组一致」，不响应不阻塞 |
| 想给同伴改的权利又怕失控 | 受邀编辑权与只读分离：受限字段（名称/备注/勾选/顺序）、可 TTL、可吊销、有使用审计 |
| 异地小组实时同步 | WebSocket 评论/投票/编辑增量广播 |

### 4. 行中——「路上想用，但行程是死的」

| 用户痛点 | 解法（代码实证） |
|---|---|
| 到了现场想改行程，打开工具却是出发前快照 | 行中今日视图：打卡/跳过/迟到一键顺延（后续站点自动重排，受 DrivingGate 约束），同伴免登录可操作 |
| 市内交通怎么走心里没底 | 市内通勤视图（相邻站点公交/步行/驾车建议） |
| 预算超没超、谁垫了钱算不清 | 行中费用记录 + 人均结余分摊（append-only 记账、四舍五入到分） |
| 忘了带东西 | 按行程隔离的打包清单（5 套预设模板 + 自定义） |
| 行程变更同伴不知道 | 事件流 append-only + PWA 通知 + 未读红点 |

### 5. 数据主权——「平台倒了，行程就没了」

| 用户痛点 | 解法（代码实证） |
|---|---|
| 行程锁死在一个平台（Wanderlog 免费版无导出、Tripnotes 关停） | 行程 JSON 导出（owner/分享令牌双路径，零令牌零凭证输出）+ 打印样式存 PDF |
| 不想把行程数据交给任何平台 | MIT 开源 + docker-compose 自托管一键部署 |

## 四、从用户视角看：系统性短板

### 🔴 A 类：功能链缺口（用户直接感知「还不够」）

| # | 短板 | 用户视角的体感 | 依据 |
|---|---|---|---|
| 1 | **只规划、不预订** | 「行程很漂亮，但酒店/门票/车票我还得自己再去比价下单——那 AI 到底帮我省了什么？」规划与执行之间断了一截 | 定位选择（README 明确「方案 C 未做」）。⚠️ 用户不关心定位，只关心少干活 |
| 2 | **价格真实性弱** | 预算明细大量「类目估算」（景点门票按类目参考价、酒店按城市基准×档位），与真实价格可能差出一倍；「预算」恰是行程里最需要可信的数字 | 免费高德 POI 不返回价格（README 诚实清单）。免费工具的宿命，但直接打击核心信任点 |
| 3 | **营业状态本质是猜测 + 用户自查** | 「周一闭馆/免费周日」这类提示基于规则库，且诚实标注「以现场为准」——诚实的另一面是把确认责任推给用户 | TimeGate/dynamic_facts 均为规则库（代码实证）。⚠️ 对「信 AI」的用户，一行免责标注挡不住一次翻车带来的信任崩塌 |
| 4 | **没有真人兜底** | 极端边缘场景（AI 反复改不对、信息互相矛盾）没有人工定制师/客服，用户只能弃用 | README 诚实承认「无 7×24 人工兜底」；工程化降级链替代不了人的判断 |
| 5 | **分享链接无访问控制** | 分享/编辑链接**无密码、无到期默认开关**，谁拿到谁看；被恶意转发无法阻止 | `task-share-gate-eval` 仍是 todo 未勾选项（代码实证：share/edit token 无密码保护） |
| 6 | **无用户评价/信任信号** | 画廊没有「这个方案被多少人用过、好评差评」信号，用户无法判断 AI 方案靠不靠谱 | gallery 靠运营标记，无评分体系（代码实证） |

### 🟡 B 类：体验层短板（摩擦劝退）

| # | 短板 | 用户视角 | 依据 |
|---|---|---|---|
| 7 | **协作身份是匿名的** | 评论/投票/编辑是「匿名令牌 + 设备指纹」，讨论时不知道谁是谁；**token 泄露即等同完全授权** | README 诚实清单原文；share/edit token 匿名模型（代码实证） |
| 8 | **截图 OCR 依赖 macOS 部署** | OCR 走 macOS Vision framework（`backend/bin/ocr_vision`）；部署在 Linux 服务器/容器时该通道失效——Web 用户「传截图 → 变成行程」在主流服务器部署下是装饰 | screenshot_import.py 平台依赖（代码实证） |
| 9 | **规划必须登录** | 「想随便试试」的用户在入口被拦；guest 试用已评估关闭（成本滥用/数据安全理由充分，但与竞品「免注册 30 秒出行程」比是摩擦 | guest-trial 评估关单记录（文档实证） |
| 10 | **Google 登录要部署方自备 Client ID** | 未配置时登录按钮隐藏——自托管者少一个入口；普通用户则只有邮箱密码一条路 | README 诚实清单原文 |
| 11 | **手机端是 PWA 壳** | 能装主屏、能推送，但体验与原生 App（锁屏 Live Activities 等）有代差 | `task-live-lockscreen-eval` 已评估降级（文档实证） |

### 🟢 C 类：工程强者但用户「感知不到」的资产（诚实记录，防误伤）

- 475+ 测试全绿 / FakeLLM 零 token——用户不在乎，但这是「敢改功能不出事故」的地基；
- T-A-O 轨迹全程可见——极少数产品能做到的透明，直接服务于「敢信」；
- 所有估算/降级/规则结果诚实标注 basis——不假装精确；
- 修订 diff 原子应用 + 整体回滚——用户敢点「让 AI 调整」；
- 夜间无人值守开发流水线——功能迭代速度的来源，也是项目健康度的证明。

## 五、一句话体检报告

**它解决的是「行程规划层」最痛的三件事：AI 行程不敢信、生成了改不动、改完了没法一起用。** 这三件事做得比绝大多数同类产品深，是目前真正的核心资产。

**但它在「从规划到执行」的链条上是断的**：不能订、价格不准、营业状态靠猜、极端情况没人救——对「只想要一份能直接执行的行程」的用户，它给的是一份**很好的草稿**，而不是**能走的路书**。

**最大瓶颈不是代码，是没有真实用户跑完一趟完整旅程**：现在所有功能都是「工程视角推演出的用户痛点」，缺一次「用户用真钱、真时间、真需求」的验证——这个缺口比任何单点功能缺失都致命（与 10-21 复盘「假设 A 未闭环」结论一致）。

## 六、若要按用户价值排序的下一个动作

| 优先级 | 动作 | 用户价值 | 成本 |
|---|---|---|---|
| 1 | **真实用户试用闭环**（发布 → 观察 → 访谈 3-5 个真实行程） | 验证/修正一切推演，最高 | 低（已有发布清单） |
| 2 | `task-share-gate-eval`（分享密码/到期） | 堵住「发出去的链接失控」的防御性缺口 | 低（已排队待评估） |
| 3 | 价格真实性升级（付费 POI / 对接真实价格源评估） | 修复「预算不可信」核心信任点 | 中（需评估供应商成本） |
| 4 | 移动端 OCR 通道（前端 OCR / 云 OCR 评估） | 修复「Web 用户传截图」的装饰感 | 中 |
| 5 | 预订闭环评估（分销 API） | 补「规划→执行」断点 | 高，且与「规划层」定位冲突——需产品决策 ⚠️ |
