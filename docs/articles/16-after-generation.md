# 生成之后：AI 行程规划的分水岭，已经移到规划后链路

> 系列第 ⑯ 篇（2026-11 新入局者实证）。前作 ⑮《收购季：规划入口的巨头化，是 2026 年最后一场收割》讲的是「规划入口被巨头收编」——本篇讲的是同一轮潮水在**独立工具**一侧的走向：2026 年 11 月的新入局者不再拼「生成行程」，而是集体把战场移到**生成之后**——验证、优化、协作、分摊、盯价、导入。分水岭不是「谁会生成」，而是「生成之后怎么办」。
> 读者：在巨头阴影下做独立产品的工程师与独立开发者。
> 数据截至 2026-11-15。

## 一、11 月中旬，三家新入局者都没在拼生成

⑮ 文讲了一个月内巨头集体收编规划入口。本周再看独立工具一侧，2026 年 11 月冒出的三家新入局者，没有一家把「AI 生成行程」当卖点：

| 新入局者 | 主打卖点 | 一句话 |
|---|---|---|
| **Butter Agent**（App Store, iPad） | 「Bring the plan you already have」粘贴已有计划 + 群组 + **账单分摊一键结清** + 开放时段占位 | 生成是默认值，重点是「把已有的计划用起来」 |
| **Stardrift**（stardrift.ai） | **多城市一条龙**（航班/酒店/活动）+ 图片/邮件导入 + Pro 付费**机票盯价** | 多城衔接 + 输入自由 + 主动盯价 |
| **Fortrip**（fortrip.ai） | 「AI travel optimizer」**验证/优化已有行程** + 专属 Transport Optimizer | 不再生成，专门检查/优化已有行程 |

把三家的功能文档并排看，共同的潜台词是：**「生成一段行程」已经不再稀缺**——ChatGPT/Gemini 免费会做、巨头 OTA 默认配置、独立工具一周冒出八个。于是差异化只能发生在行程生成**之后**：

- **Stardrift 的 2026-09-15 changelog**：图片上传（预订确认单/行程截图 OCR 进行程）、邮件转发（个人转发地址，不连 Gmail 的用户可用）、付费订阅**机票价格盯梢**（实时价格变化告警）、酒店精确房型直接预订。
- **Butter Agent**：规划前先展示「它理解了啥 + 会用多少 credits」；研究真实地点钉在地图上、保留引用网页；细化用自然语言、回退免费；支持**开放时段占位**（「2–4pm around Shibuya, something relaxed」）；群组 + 账单分摊一起旅行、**分摊每笔费用并一键结清**（v2.0 全新 UI）。
- **Fortrip**：不是再生成一个行程，而是**检查/优化已有的行程**——路线顺序、酒店日期、总成本；多城市行程把城市顺序/天数/交通组合/酒店排布**当作一个路线一起规划**（不是三个独立行程拼起来）；「It asks before it assumes」——影响行程的决策点暂停询问并给推荐。

这三家的动作，和过去三周我们反复看到的信号完全同向：agentic 预订收购潮（⑮）、43% 缺陷研究（⑫）、诚实边界（⑬）。**「生成之后怎么办」正在成为 2026 年的分水岭。**

## 二、Fortrip 把「验证/优化」做成了独立品类

三家里面最值得我们盯的是 Fortrip——它不是把「验证」当行程的一个功能，而是把**「检查/优化已有行程」直接做成了产品本身**。

定位是「AI travel optimizer」：输入一段已有行程 → 它检查路线顺序、酒店日期、总成本，并给出优化建议。这和我们 ⑫ 文讲的「质检是工程，不是 prompt 运气」是同一个方向，但它往前走了一步：**验证不是附属，而是入口。**

Fortrip 的另一半是**多城市交通优化**：城市顺序、天数、交通组合、酒店排布作为一个路线一起规划（「cities, transit legs and pacing planned as one route, not three separate trips stapled together」），有专属 Transport Optimizer。Stardrift 也是这个路数（多城市 + 交通顺序一条龙）。

翻译成工程语言：**「行程」这个对象正在从「一串站点」升级为「一串城市段 + 段间交通 + 段内站点」的层级结构**。单城市单日排程是平面问题，多城市是把平面问题叠成层级问题——城市间交通怎么接、到港 vs 首站开放怎么衔接、城市顺序怎么排才不绕路。

## 三、我们一直在做的，正是「生成之后」

把三家新入局者的卖点摊开，对照我们仓库里已经上线的东西——大部分不是新差距，而是**我们过去三周已经走过的路**：

| 新入局者卖点 | 我们的实现（可核对） |
|---|---|
| Fortrip 验证/优化 | **四维质检 + T-A-O trace**：`TravelCriticAgent`（`app/agent/agents.py`，四维打分 + `passed` 闸门）+ `time_validation`（营业时间门 + 餐饮锚定 + 体力系数）+ `dynamic_facts`（周一闭馆特例表）+ `repeat_detector`（RepeatGate，同天/相邻天重复检测）+ `weather_validation`（雨天/酷暑 → 室内替代建议）——全部确定性规则库，零额外 LLM 成本，可单测 |
| Butter 群组 + 分摊 | **协作 + 分摊**：`collab_service`（投票 + 渐进式共识 `_consensus_threshold`，多数即推进）+ `expense_service`（多币种费用记录 + `compute_balance` 人均结余）——没有「一键结清」资金动作（零资金边界，见⑮） |
| Stardrift 多城一条龙 | **多城市段排程**：`app/services/multi_city.py` + `app/agent/pipeline.py` 的 `apply_multi_city`（按城市段分组排程 + 段间交通占位 + 质检衔接校验 + plan.multi_city）——还没把「城市级重排/交通组合优化」做成显式入口（见第五节） |
| Stardrift 图片/邮件导入 | **四通道导入**：`note_import`（粘贴文本）/ `email_import`（粘贴预订邮件文本）/ `screenshot_import`（OCR）/ `link_import`（链接收藏）/ `social_import`（社交分享文本），全部零凭证 |
| Butter 粘贴已有计划 | 🟡 我们有 `social_import`/`email_import` 的「整段文本 → 结构化」，但缺「粘贴整段已有行程计划 → 天/时间/地点骨架 → 站点勾选并入」的专门解析（见第五节） |
| Butter 开放时段占位 | ❌ 我们没有「2–4pm 随意」这种显式留白占位语义（`pace=relaxed` 是节奏倾向、`plan_b.Relaxed` 是过满日变体，均不是用户显式声明的留白时段） |
| Stardrift/Mindtrip 盯价 | ❌ 免费价格提醒 API 不存在（10-10 已评估），降级为**行程内事件主动通知**（修订/协作事件推送 owner，复用 share 链路） |

**结论：我们的「生成之后」能力已经覆盖了这轮新入局者的大半卖点**——质检 trace、修订闭环、协作投票、行中三件套、多币种分摊、预订台账 + 节奏库、导出（JSON/ICS/PDF）。这不是巧合：过去三周我们从 ⑫⑬⑭⑮ 的竞品信号里一步步把「规划后链路」做成了产品主体。

## 四、真正的差距：不是功能，是「可感知」

但把话说完整，「生成之后」这轮分水岭对我们还有一个更尖锐的提醒——**能力要长在用户看得见的地方**。

对照三家新入局者的产品叙事：

- Butter 把「开放时段占位」做成**规划前的输入**（用户主动说「2–4pm 随意」），是用户在第一屏就能感知的能力；
- Fortrip 把「验证/优化」做成**独立的入口**（丢一段已有行程进去，它检查），是用户带着已有计划来的第一落点；
- Stardrift 把「多城 + 导入 + 盯价」做成**一条龙的对话流程**，用户从输入那一刻就在用它的差异化。

而我们的规划后能力（质检/修订/协作/分摊）大多长在**行程生成之后**的详情页里：质检卡在评分卡之后、协作在分享链接里、分摊在行中费用里。用户要「生成一次行程、往下翻、点开看」，才摸得到这些。**这不是功能差距，是感知差距**——能力在，入口不在。

这正是 11-14 决裁的 to-C 上线验证计划（`docs/plans/2026-11-15-core-value-launch.md`）要解决的事：本项目还没有真实用户、没有外部验证信号（0 stars / 0 forks，数据库里 0 gallery / 0 rating）。工程能力已被 1,139 个测试自证，产品价值从未被验证。**上线 → 真实用户走完一次真实规划 → 看激活漏斗，比再堆任何功能都重要。**

## 五、候选池里的四个新差距（冻结期内不排期，解冻后评估）

11-15 竞品分析把四个新功能差距登记进候选池（`docs/night-build-todo.md` §2，Q11 冻结期内不晋升）：

1. **task-open-slot-eval（开放时段占位）**：Butter「2–4pm around Shibuya 随意」是显式留白占位语义，我们只有 `pace=relaxed` 节奏倾向。评估点：PlanRequest/stops 加「时间段 + 自由度 + 偏好类别、无固定 POI」占位 → 排程/质检/修订链路如何表示（不打破 DrivingGate/TimeGate 确定性约束），最小版 = 占位透出 + 排程不硬塞站点 + 质检豁免逻辑。规模 M（拆 2 夜）。
2. **task-multicity-optimizer-eval（多城市交通优化器入口）**：Fortrip/Stardrift 主打「city order + transit legs + pacing as one route」+ Transport Optimizer；我们有 `multi_city.py` 段排程底座 + `day_optimizer`（日内站点级），缺「调整城市顺序/交通组合」的优化动作。评估点：城市级重排（复用 day_optimizer 贪心 + DrivingGate 语义）+ 段间衔接质检（到港 vs 首站开放，linking time_validation）。
3. **task-price-watch-mini-eval（轻量价格盯梢，零凭证中间档）**：Stardrift Pro 盯价 / Mindtrip Personal Assistant 盯价两个新实证；10-10 已评估免费价格提醒 API 不存在（Google Flights 需生态登录、高德无价格提醒、Amadeus 付费）并降级为行程内事件通知。本轮不推翻，补一个零凭证中间档：对用户已录入的预订（booking 表已含金额/日期）+ 规则汇率，做「行程内价格台账 + 波动提示」（不接外部实时价，只对用户自己录入的金额做基线/变更提醒，复用 trip_events）。
4. **task-paste-any-plan-eval（粘贴任意已有计划 → 结构化行程）**：Butter 主打「paste a plan from Notes/chat/doc → 保留天/时间/地点 → 钉到真实地点 → review 后才添加」；我们四通道导入是「单通道结构化提取」，缺「整段已有行程计划 → 一站一站点位保留」的粘贴解析。评估点：复用 `note_import` 敌意剥离 + 行程骨架识别（天/时间/地点行 → 候选站点 → 勾选并入），与 email-import「零凭证粘贴版」同构。

四个差距都指向同一个方向：**不是要新引擎，是把已有的「生成之后」能力，前置到用户输入的那一刻。** 这也正是「生成之后」分水岭给独立工具的唯一正解——能力可以后置，入口必须前置。

## 六、给独立开发者的判断

1. **别再堆生成，去堆「生成之后」的入口。** 新入局者已经把「生成」做成默认值。Fortrip 把验证做成入口、Butter 把已有计划做成入口、Stardrift 把多城/导入/盯价做成输入——**入口前置 = 让用户第一次用就看到你的差异化**。能力后置 = 用户看不见 = 等于没有。
2. **质检、修订、协作、分摊，是这一轮的共同护城河。** 三家新入局者没有一家做全四维质检/修订闭环/诚实标注（⑫⑬ 已论证巨头也不做），我们全部在案且是确定性规则库（零 token、可单测）。这轮「生成之后」分水岭没有改变 ⑮ 的结论——深度 + 中立仍是独立工具仅剩的缝隙——只是把「深度」的定义从「生成好」推到了「规划后链路」。
3. **在没验证过之前，先别急着补差距。** 四个新差距都是「评估 → 最小版」的候选，但项目 0 外部验证信号的现实不变：**先把已有能力上线，让真实用户走一次真实规划，再谈把差距做成功能。** 上线验证（14 天判定线：20 访问 / 5 规划 / 2 分享）是比任何新功能都大的杠杆。
