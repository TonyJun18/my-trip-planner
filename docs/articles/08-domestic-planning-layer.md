# 国内 OTA 也在做 AI 行程了——独立规划层为什么还能活

> 写给：AI 行程/规划类产品的产品经理和工程师，以及想在国内 AI 旅行赛道找差异化的小团队。
> 一句话结论：2025-2026 年，携程、去哪儿、马蜂窝、飞猪集体把「AI 行程」做成了一站式「规划即预订」漏斗的入口。跟大厂拼预订闭环没有胜算；独立工具的机会在**规划本身的深度与服务质量**——可修订（diff）、可验证（质检 trace + 透明预算）、可协作、可导出、不受平台库存绑架。上一篇文章（07）讲海外格局，这篇是国内姊妹篇。

## 一、国内战场：OTA 已经把手伸进了规划层

海外（Mindtrip agentic 机票、Expedia 收购 Layla、Tripnotes 停运）的信号是「规划是入口，预订才是商业闭环」。国内更直接——OTA 们把 AI 行程这层入口**已经做成了自家生态的一部分**：

1. **携程 AI 行程助手**（2026 正式铺开）—— 一站式「规划到预订」：20M+ POI、实时交通/门票/酒店整合、**画布式编辑**（重命名/重排/替换/删除/备注）、常驻 AI 浮动按钮实时建议、地图路线预览、三问起步、可导入 Trip.com 历史订单、**人工定制师团队兜底**。短板：需登录、绑定携程生态、无质检透明、无跨会话记忆（弱）。
2. **去哪儿 AI 旅行工具箱**（2025-09 上线）—— 「一个核心助手 + N 个细分场景助手」（行程规划助手 / 机票 AI 小驼 / 酒店售后 AI 客服）、**小红书笔记导入生成个性化方案**（种草 → 行程转化）。短板：AI 回复偏简略、需登录、无协作/导出能力弱。
3. **马蜂窝 AI 路书 / AI 小蚂**（2025-2026 持续迭代）—— **主动提问**（选择题引导需求）、**行程备选方案（Plan B）** 与**避峰策略**（国庆期用户最关注的两个功能）、对接「当地指路人」真人专家一对一、博主实测数据反哺（踩雷按钮）、15 年真实旅行数据（游记语料）。短板：偏向目的地内容生态，规划产物导出/协作弱，无开放 API。
4. **飞猪 AI 问一问**（2025，多智能体驱动）—— 8 个细分角色（行程助手/路线定制师/交通顾问/酒店顾问/攻略达人/本地导游/预算管理师/服务保障专员）——**与我们的多 Agent 单职责编排同构**；多模态输入（文字/语音/方言）、**手绘攻略分享图**、实时位置本地生活服务。短板：绑定飞猪交易生态、无质检 trace、规划产物不可导出为结构化数据。

把这些拼在一起，信号非常清楚：**国内 OTA 已经把 AI 行程做成了「规划即预订」漏斗的入口**。携程画布 + 人工定制师、去哪儿小红书导入、马蜂窝路书 + 指路人、飞猪 8 角色多智能体——每一家都在把用户从「想要一个行程」一路引导到「在自家生态里下单」。

## 二、为什么独立工具不该跟这局牌

### 预订层是重资产，OTA 天生会赢

| 维度 | 规划层（Plan） | 预订层（Book，OTA 的地盘） |
|---|---|---|
| 核心资产 | 行程生成、修订、质检、协作 | 实时库存/票务、支付、价格预测 |
| 数据要求 | POI/天气/距离（开放或低成本） | 航司/酒店 GDS、实时价格、退改规则 |
| 信任成本 | 中（错了用户自己改） | 高（订错了要赔） |
| 履约 | 无（用户自行决定） | 有（支付、出票、售后、客服） |
| 典型玩家 | 我们、Wanderlog、MonkeyTravel | 携程/去哪儿/飞猪、Hopper、Expedia |
| 小团队可行性 | ✅ 可行 | ❌ 极难（重资产、合规、资金） |

预订层的护城河是**多年票务数据和生态绑定**，独立团队不可能在「订得更便宜」上赢 OTA。跟 OTA 拼「规划即预订」，等于用轻资产去撞重资产。

### OTA 的 AI 行程，先天有四个「做不深」的地方

1. **修订 = 动了自家库存**。OTA 的行程紧绑门票/酒店/交通，用户改行程意味着重算价格库存，所以 OTA 的「修订」通常是一次次重新生成，而不是细粒度、可回滚的修订。
2. **数据绑定 = 行程不自由**。携程行程绑定携程生态、去哪儿绑定小红书导入、飞猪绑定交易——你的行程数据被锁在平台里，导出弱、协作弱。
3. **不透明 = 黑盒推荐**。OTA 推荐酒店/景点有流量分成动机，且没有质检 trace、没有评分解释。
4. **无跨会话记忆 / 弱个性化**。OTA 的核心是交易，不是记住你的偏好。

## 三、独立规划层的生存策略：把规划做深

### 策略一：可修订——AI 出 diff，代码执行（欢迎用户改）

```python
# backend/app/services/revise_service.py
async def revise_trip(db, trip_id, message, *, owner=None, provider="auto"):
    # 1) AI 只生成结构化 diff（PlanReviseAgent，无工具、失败可自纠正）
    revise = await plan_revise_agent({...}, current_plan, provider=provider)
    # 2) 代码原子应用（存在性/类型/位置校验，任一失败整体回滚）
    _apply_diff(trip, diff)
    # 3) 落库 + 预算代码重算（LLM 估值不可信）
    await _recompute_budget(db, trip)
    await db.commit()
```

### 策略二：可验证——价格真实度与质检闭环

OTA 的行程是黑盒，我们用两条路对抗：

**价格真实度**：酒店参考价用代码确定性估算（城市基准价 × 档位倍率 × 评分修正），不靠 LLM 瞎报：

```python
# backend/app/services/budget_service.py
def estimate_hotel_cost(name, city=None, *, rating=None) -> float:
    base = _HOTEL_CITY_BASE.get(_match_city(city), _HOTEL_FALLBACK)  # 城市基准价
    multiplier = 1.0
    for kw, m in _HOTEL_TIER:            # "五星"×2.8、"经济"×0.7 ……
        if kw in name:
            multiplier = m
            break
    ...
```

前端标注「参考价，以实际询价为准」——我们不会假装帮你订到最便宜的酒店，但保证预算不是空壳。

**质检闭环**：Planner 产出后由 TravelCriticAgent（无工具质检专家）按日程/预算/地理/完整性四维评分，不过审带反馈重生成（最多 2 轮后强制定稿，质检失败自动降级放行）：

```python
# backend/app/agent/agents.py
CRITIC_PASS_SCORE = 80            # 质检通过线
# Evaluator-Optimizer：Planner 生成后交给 TravelCriticAgent 评审，
# 反馈回喂 Planner 修稿，≤2 轮强制定稿；Critic 故障降级放行
```

配合前端实时 T-A-O（Thought-Action-Observation）轨迹（`frontend/src/views/PlanWizard.vue` 的"查看 AI 专家协作过程"面板），**用户能看到每个 Agent 在干什么、为什么这么生成**。对比 OTA 的黑盒推荐，透明是最便宜的护城河。

### 策略三：可协作——把多人决策留在规划层

```python
# backend/app/services/collab_service.py
async def _belongs_to_trip(db, stop_id, trip_id) -> Stop:
    """校验站点属于该行程（防止跨行程投票）。"""
    ...
```

一行 `share_token` + 评论 + 站点 👍/👎 投票（幂等可翻转）+ 受邀编辑权（edit_token 与只读 share_token 分离），把「群里十个链接来回发」变成「一个链接大家投票定行程」——规划层的协作不需要拼实时协同编辑，先把决策问题解决。

### 策略四：可导出——行程是用户的资产

`frontend/src/utils/export.js`（html2canvas + jsPDF）支持一键导出图片/PDF，行程不锁在账号里。

### 策略五：可自托管、开源——OTA 永远做不了

整个仓库 MIT 开源（github.com/TonyJun18/my-trip-planner），没有账号墙、没有数据锁定。"你的行程是别人家的流量"这句话在 OTA 语境里是商业模式，在开源工具里是反面教材。

## 五、可复用的模式

| 决策 | 落地方式 | 收益 |
|---|---|---|
| 不做预订闭环 | 只做规划层（生成/修订/质检/协作/导出/自托管） | 避开重资产，专注体验深度 |
| 修订走 diff + 原子应用 | AI 出指令、代码执行（revise_service） | 可信、可回滚、可解释——OTA 因库存绑架做不了 |
| 质检做成闭环 | TravelCritic 四维评审 ≤2 轮（agents.py） | 输出质量有闸门，不无限烧 token，且透明可溯 |
| 价格用代码估算 | 城市基准价 × 档位倍率（budget_service） | 可解释、可测试、无外部依赖 |
| 协作做轻量版 | share_token + 评论 + 投票 + 受邀编辑权（collab_service） | 多人决策可闭环，不碰协同编辑复杂度 |
| 透明做资本化 | MIT 开源 + T-A-O 轨迹 + 参考价标注 + PDF/图片导出 | 行程是用户资产，不是平台流量 |

## 小结

- 国内 OTA（携程/去哪儿/马蜂窝/飞猪）已经把 AI 行程做成了「规划即预订」的漏斗入口，且各有生态绑定——跟它们拼预订闭环是死路。
- 独立工具的机会在**规划本身的深度**：可修订（diff+原子应用）、可验证（价格估算+质检 trace）、可协作（投票+受邀编辑）、可导出（图片/PDF）、可自托管（MIT 开源）。
- 这五件事 OTA 因为商业模型（库存/佣金/流量）**天然做不深**，而它们正是规划层用户真正在意的服务质量——**OTA 把入口做成了漏斗，我们把入口做成了产品**。
