# 第一次尝试就翻车：AI 旅行工具的信任缺口

> 系列第 ⑬ 篇（前作 ⑫《AI 旅行翻车实录：从闭馆景点到悬崖救援，规划工具的质检底线》）
> 读者：做 AI 消费级产品的工程师与 PM；关心「为什么用户试一次就再也不回来」的人。

## 一、先看一组数字

- **Expedia**：66% 用户不信任 AI 预订；
- **YouGov**：仅 30% 对 AI 旅行规划感到舒适，且同比下滑；
- **McKinsey**：已使用者中 84% 认为体验改善；
- **MonkeyTravel 的一句总结**：「Most people never get past the first attempt. That is a product problem.」

这四组数字放在一起是一个尴尬的结构：**用过的人说好，没用过的人不信，而大多数人卡在「第一次」**。信任不是靠品牌广告建立的，是靠第一次尝试那 10 分钟建立的。

## 二、信任崩掉的三条路径

从用户视角，第一次尝试出问题只有三条路径：

1. **不可验证**：行程看起来很美，但不知道哪个数字是真的。预算 3000 是怎么算的？推荐这家店凭什么？——用户只能选择「全信」或「全不信」，最终选后者。
2. **不可修订**：发现某天太赶，只能从头再来一遍；或者改了一处，别处悄悄变了。用户失去控制感。
3. **套模板**：换个城市、换个季节，出来的行程结构一模一样。用户立刻识别出「这是模板」，信任归零（36氪把「撞脸/套模板/数据孤岛」列为 AI 旅行产品同质化三症）。

对应的工程答案不是「更会说话」，而是三个可感知的属性：

| 信任属性 | 工程实现 | 用户能感知到什么 |
|---|---|---|
| **可验证** | T-A-O 轨迹 + `basis` 来源标注 + 确定性规则库 | 「这条警告是规则算的，不是 AI 猜的」 |
| **可修订** | AI 出 diff、代码原子应用、失败整体回滚 | 「我一句话就改了，而且能看到改了什么」 |
| **不套模板** | 主动提问 + 跨会话画像 + 行为记忆 | 「它记得我上次喜欢慢节奏」 |

## 三、可验证：把「AI 说的」降级为「有依据的」

我们的做法是**每一条结论都带出处**：

- 预算：`budget_service.compute_budget` / `estimate_hotel_cost` 用城市基准价 × 档位倍率 × 评分修正，**不经过 LLM 估值**；界面标注口径「住宿按城市基准价估算」。
- 时间：`time_validation.py` 的 warning 标 `basis=rule_based`，并明说「真实营业时间以 POI 现场为准」。
- 动态事实：`dynamic_facts.py` 的周一闭馆/免费日/节假日提示同样标规则库来源。
- 数据采集：trace 里每个 observation 带 `source=amap` / `source=tavily` / `source=wttr.in`，降级时明确写「FoodAgent 失败，代码兜底」。

一个具体细节：`/health` 在数据库故障时返回 `degraded` 而不是 500。用户看到的是「服务在，但数据可能不新鲜」——这比假装一切正常诚实。

## 四、可修订：修订是一等公民

传统做法是「重新生成一版」，我们的做法是把修订做成独立能力：

1. 用户一句话（「第三天太赶了，西湖只留半天」）；
2. `PlanReviseAgent` 只产出结构化 diff（replace / add / remove / reorder）；
3. `revise_service._apply_diff` 先校验全部动作（目标存在性/类型/位置），任一失败**整体回滚**；
4. 预算由代码重算，修订后过 DrivingGate 与 TimeGate；
5. 前端展示 diff 摘要与质检 trace。

关键在**原子性**：LLM 直接改库会产生半生效状态（改了两处、第三处失败），用户看到的是「行程坏了」。代码执行 diff 则天然可回滚。

配套还有两层：手动细粒度编辑（站点行内改、整日重排）和受邀编辑（`edit_token` 受限字段），覆盖「不想跟 AI 说话、只想改个字」的场景。

## 五、不套模板：先问，再记

- **主动提问**：`questions` 让用户在规划前回答人群/节奏/避峰/备选方案，答案并入上下文（`agents._questions_text`）；
- **画像记忆**：`profile_service` 跨会话保存偏好，规划时自动注入；用户手动改画像不会覆盖系统观察（声明与观察分离）；
- **行为记忆**：`preference_service` 从修订/打卡行为推断偏好，有界滚动（最多 100 条信号）+ 新鲜度签名，不每次全量重算；
- **灵感入口**：没想好去哪的用户，用 23 目的地规则库推荐（零 LLM、可测试），选中后预填表单——**入口不同，但都导向同一条高质量生成流程**。

## 六、信任是可以设计的

把上面三件事落到产品语言：

> 「我们不是让你相信 AI，而是让你**不需要相信**——每条结论有来源，每次修改可回滚，每份行程按你的习惯长出来。」

这也是 ⑫ 篇质检底线的商业面：质检不仅减少错误，它把「错误」变成「可见的警告」。用户看到 3 条 warning，比看到一份没有 warning 的完美行程更信任这个工具。

## 七、给同行的检查清单

- [ ] 预算/时间/距离这些数字，是代码算的还是模型写的？
- [ ] 每条 warning 有没有标来源（规则/数据源/模型）？
- [ ] 修订失败时，是整体回滚还是半生效？
- [ ] 有没有「未知就沉默」的约定，还是遇到未知就编？
- [ ] 用户能不能在 30 秒内看到「这次规划依据了什么」？

## 八、2026-11 更新：渗透率上来了，信任没跟上

三个月后补的一批实证（2026-07 ~ 2026-11）让结论更刺眼：**用的人变多了，但对「规划之后那一步」的信任没有同步上来**。（原文四组数据保留不动，以下是增量。）

1. **渗透率**：Allianz Partners 调查（2026-07-23，经 Hotel Dive 报道）——**37% 美国旅客已用 AI 规划旅行**，并期待全程「快、直觉、移动优先」的交互。尝鲜期结束了。
2. **通用 agent 带不来成交**：Airbnb 2026 Q3 电话会（2026-11-05），Chesky 明确说 Meta Muse 这类通用 AI agent 给 Airbnb 带来的**流量很少、成交更少**；同时断言「**聊天窗口是规划旅行的错误形态**」——行程涉及地图、照片、日期和群体决策。这条同时印证本文两点：①「更会说话」不构成信任；② 规划界面必须是专用、可核对的结构化界面。
3. **巨头自己也承认用户不买账**：Yahoo 报道的标题就是结论——「Hilton's AI Trip Planner Wants To Book Your Travel. **Customers Aren't So Sure Yet.**」（2026-11-07）；同期 Hilton CIO 公开谈 tokenomics。信任缺口不分规模，它卡在「第一次尝试」，不在品牌。
4. **供给真实度成为新赛点**：Cape Town Tourism 宣布免费 AI 行程规划器（2026-11-05 公布，2027-01 上线，第二阶段加预订），主打「用本地专业度做出比 ChatGPT 更地道、超出必去景点的行程」。这与我们的判断同向：**真实度是供给侧问题，不是提示词问题**。

对应到第二节的三条路径，工程答案没变，只是更具体：

| 新证据 | 它说明什么 | 我们的工程对应（都可核对） |
|---|---|---|
| 37% 已用 AI 规划 | 第一次尝试的样本量变大，翻车成本随之放大 | 四维质检 + `basis` 口径标注：第一次就给可读的警告，而不是完美的假象 |
| 「chat 窗口是错误形态」+ 通用 agent 成交更少 | 界面形态与信任绑定，对话不是终点 | 结构化日卡 + 地图 + 修订 diff 预览：用户核对的是**行程对象**，不是 AI 的一段话 |
| Hilton「用户还不确定」 | 品牌解决不了信任 | 可修订（diff 原子应用、失败整体回滚）+ 不套模板（主动提问 / 画像 / 行为记忆） |
| 城市旅游局主打本地专业度 | 供给真实度是真差异化 | `dynamic_facts` 特例表 + 规则库「未知就沉默」的约定 |

一句话更新：**2026 年的竞争不再是「谁的 AI 会写行程」，而是「谁的行程经得起核对」。**
