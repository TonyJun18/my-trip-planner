# 预算是 AI 行程工具最不诚实的部分

> 写给：AI 行程/规划类产品的产品经理和工程师，以及每个被 AI 行程预算「骗过」的旅行者。
> 一句话结论：AI 行程工具生成的预算，多数是三种不诚实的排列组合——LLM 拍脑袋（无来源、无口径，错了也没人负责）、过期基准（pre-2023 的酒店均价拿来当 2026 年的参考）、付费墙（把「估算」本身变成 Pro 功能）。预算的不诚实不是技术问题，是产品选择。规划层工具的正确姿势是**标注口径的诚实估算 + 修订联动重算 + 估算 vs 实际可验证**——预算不是用来「显得便宜」的，是用来「敢信」的。

## 一、先看三个翻车现场

预算是一趟 AI 行程里用户最先看、最后信的东西之一。但 2026 年 9 月的竞品抽样里，预算恰好是最常被「糊弄」的模块：

**1. iPlan.ai：偏差 20-30%，基准是 pre-2023 的老数据。** 评测直接点名它的预算估算粗糙——基于 2023 年以前的基准数据，对 2026 年的旅行者来说，这个数字既不反映涨价，也不反映新开的平价选择。偏差 20-30% 是什么概念？一趟 5000 元的预算，实际可能要 6500——不是小误差，是「出发前以为够、到地方才发现差一晚酒店」的量级。

**2. Wonderplan：预算基于「一般目的地数据」而非实时价格。** 它诚实承认了这一点——但承认不等于可用。「一般目的地数据」意味着杭州和宁波、三亚和三亚湾，在你的预算里可能没有任何区别。对规划来说，这种粒度约等于没有。

**3. Wandercrafted：预算估算在付费墙后面。** 免费版能看行程，但「预算估算、天气、协作编辑」都是 Pro（$49.99/年）功能。把一个「诚实告诉用户这趟要花多少钱」的基本能力做成付费点——这不是产品决策，是商业模式把诚实标了价。

三条放在一起，信号很清楚：**在 AI 旅行赛道，预算是最容易被牺牲诚实的模块**——因为它既难（实时数据源、价格波动、动态定价），又不在预订闭环的生死线上（预算报低了用户也不当场退款）。于是各家默认选择「凑合」：能估就估，估不准也无所谓，反正没人对预算负责。

## 二、三种不诚实，三种生意经

| 不诚实类型 | 代表做法 | 谁在这么做 | 用户代价 |
|---|---|---|---|
| **拍脑袋型** | LLM 在生成行程时顺手编一个总价，无来源、无口径、无校验 | 多数依赖 LLM 直接输出预算的工具 | 数字看起来精确（¥4,328.50），实际是零信息；问了就是「AI 估算」 |
| **过期基准型** | 有估算逻辑，但基准价格来自几年前，或粒度粗到「一般目的地」 | iPlan.ai、Wonderplan 等 | 看似有依据，实际与当前价格系统性偏离——而且偏差方向不可知 |
| **付费墙型** | 估算能力本身是付费功能，免费用户只有「没有预算」 | Wandercrafted 等 | 基础能力被商业模式绑架；免费用户连「大概多少钱」都不知道 |

注意这三者和「预订层」的关系：对预订层玩家（OTA、agentic 预订），**预算往低报是有利的**——便宜的估算把用户引入比价和下单流程，真实价格在结算页面才现形。这不是阴谋，是漏斗设计的自然产物。但对规划层工具，预算的价值恰恰相反：**用户拿你的预算去做决策，数字敢不敢信，决定产品敢不敢用。**

## 三、诚实的预算长什么样：口径、代码、可修正

我们（my-trip-planner，FastAPI + LangGraph + Vue3，开源于 github.com/TonyJun18/my-trip-planner）在规划层做预算，原则有三条：**估算不靠 LLM 张嘴、口径必须标注、修订必须联动重算。** 以下代码引用均与仓库实际一致（main 分支）。

### 原则一：代码确定性估算，不靠 LLM 拍脑袋

预算里最容易「拍脑袋」的是酒店。酒店价格受城市、档次、评分、淡旺季影响，LLM 报出的「每晚 ¥438」没有任何依据。我们改成纯代码的确定性估算——**同样的输入，永远得到同样的输出**：

```python
# backend/app/services/budget_service.py
_HOTEL_CITY_BASE = {
    "北京": 520.0, "上海": 560.0, "杭州": 430.0, "成都": 360.0, ...
}
_HOTEL_FALLBACK = 380.0  # 未知城市兜底（接近全国中档均价）

_HOTEL_TIER = [
    ("奢华", 3.2), ("豪华", 2.6), ("五星", 2.8), ("国际", 2.2), ...
    ("经济", 0.7), ("青旅", 0.55), ("招待所", 0.5), ...
]

def estimate_hotel_cost(name, city=None, *, rating=None) -> float:
    base = _HOTEL_CITY_BASE.get(_match_city(city), _HOTEL_FALLBACK)
    multiplier = 1.0
    for kw, m in _HOTEL_TIER:          # 「五星」×2.8、「经济」×0.7……
        if kw in name:
            multiplier = m
            break
    cost = base * multiplier
    if rating is not None:             # 高评分上浮 15%，低评分下浮 15%
        if rating >= 4.5: cost *= 1.15
        elif rating <= 3.5: cost *= 0.85
    return round(cost, 2)
```

这套模型可解释、可测试、**不需要任何外部价格 API**。杭州经济型酒店 = 430 × 0.7 = ¥301；杭州五星 = 430 × 2.8 = ¥1,204；测试里写死断言，改模型就改测试（`backend/tests/test_budget_service.py`）。源头不是实时房价，但它的偏差是**可知、可解释、可修正**的——偏差在口径里，不在黑盒里。

### 原则二：口径必须标注——「估算 vs 实际可验证」

光有估算还不够，用户需要知道**这个数字是怎么来的、可信到什么程度**。所以每份含酒店的预算都带 `estimate_basis`——来源、基准说明、置信度：

```python
# backend/app/services/budget_service.py
def hotel_estimate_basis(estimated_count: int) -> dict:
    return {
        "source": "city_base_2024",                    # 基准口径：2024 城市中档均价
        "base_note": "城市中档酒店基准价 × 档位倍率（静态口径，非实时房价）",
        "confidence": "medium",
        "estimated_count": estimated_count,
        "actual_count": 0,                             # 实际确认数：0 = 纯估算
        "updated_at": "2026-09-26",
    }
```

前端预算卡（`frontend/src/views/TripDetailView.vue` / `ShareView.vue` 的 budget-card）展示总数时明确标「估算」（环形图内 `ring-label` 即 i18n `common.estimated`）；后端契约在含酒店站点时随预算返回 `estimate_basis`（来源/基准/置信度/估算数量），**口径已全量透出到 UI**：预算卡底部「预算口径」行渲染 `住宿约 ¥xxx/晚×N（城市基准价估算）`与 `大交通按参考价×2`（i18n `share.basis*` 键，zh/en 双语）。酒店参考价的「参考价，以实际询价为准」标注约定，写在 `backend/app/agent/agents.py` 的 `_normalize_hotels` 注释中。**我们不会假装「帮你订到最便宜的酒店」——我们只说「这个数字怎么来的、别把它当最终账单」。**

### 原则三：修订必须联动重算——预算跟行程一起变

行程是活的：用户说「第三天西湖改成半天，晚上加楼外楼」，预算不能停留在 AI 第一次生成时的旧值。每次 AI diff 修订落地后，**代码重算预算**，而不是让 LLM 重新估一遍：

```python
# backend/app/services/revise_service.py
async def _recompute_budget(db: AsyncSession, trip: Trip) -> None:
    """修订后由代码重算 TripPlan.plan_data.budget（有快照则同步更新）。"""
    all_stops = [
        {"name": s.name, "type": s.stop_type, "estimated_cost": float(s.estimated_cost or 0)}
        for d in trip.days for s in d.stops
    ]
    budget = compute_budget(all_stops)
    ...
```

同样地，**生成阶段**编排层在把行程交给质检前，也先用真实站点列表覆盖 LLM 的估值（`backend/app/agent/agents.py`）：

```python
# 预算校准前置：先以真实 stops 计算预算（覆盖 LLM 估值），再交给质检
all_stops = [s for d in candidate.get("days", []) for s in d.get("stops", [])]
candidate["budget"] = agent_tools.compute_budget(all_stops)
```

两道重算保证一件事：**任何时刻用户看到的预算，都是当前行程在代码口径下的确定性结果，而不是某次 LLM 输出的残留物。** 预算和行程之间，不存在「忘了更新」的窗口。

## 四、诚实估算的工程账

| 决策 | 我们怎么做 | 收益 | 成本/局限 |
|---|---|---|---|
| 酒店估算用代码而非 LLM | 城市基准价 × 档位倍率 × 评分修正（`budget_service.py`） | 可解释、可测试、零外部依赖、偏差可知 | 静态口径，非实时房价；淡旺季/涨价不敏感 |
| 口径随预算一起返回 | `estimate_basis`（source/base_note/confidence） | 用户可判断「信多少」；「估算 vs 实际可验证」 | 需要前端展示约定，否则白做 |
| 修订后代码重算预算 | `_recompute_budget`（`revise_service.py`） | 预算永远与行程同步，无残留旧值 | 每次修订多一次纯计算（成本可忽略） |
| 生成时覆盖 LLM 估值 | `agents.py` 编排层校准前置 | LLM 只负责「排什么」，不负责「多少钱」 | 站点 `estimated_cost` 缺失时仍可能为空（有兜底） |

**关键心态**：预算诚实不是「把数字估准」——在静态基准下不可能估准实时房价，任何规划层工具都不该假装能。诚实是**把估算的边界说清楚**：这个数是什么口径、什么置信度、怎么修正。用户的信任不来自数字精确，来自「这个工具没有在预算上骗我」。

## 五、给同行的一份「预算诚实清单」

写完这篇，我们把「预算诚实」拆成可自查的清单：

1. **预算数字有源头吗？** 是 LLM 顺手编的，还是代码从明确模型算出来的？（前者：任何数字都不可审计）
2. **口径对用户可见吗？** 用户能不能知道「参考价」「估算」「非实时」？（看不见口径 = 默认被当成真价）
3. **修订后重算吗？** 改完行程，预算还停在旧值吗？（残留旧值 = 行程与预算失信）
4. **估算 vs 实际可验证吗？** 有没有「估算数量 vs 实际确认数量」的对比？（没有对比 = 永远无法校准自己的模型）
5. **把估算当付费点了吗？** 如果是，想清楚：你在为「诚实」收费，还是在为用户的不信任买单？

---

## 小结

- 2026 年 9 月竞品抽样里，AI 行程预算普遍不诚实：iPlan.ai 偏差 20-30%（pre-2023 基准）、Wonderplan「一般目的地数据」、Wandercrafted 把预算估算放进付费墙。
- 不诚实的根源是商业模式：对预订层漏斗，低估预算有利；对规划层，预算敢不敢信决定产品敢不敢用。
- 我们的路线是「标注口径的诚实估算」：**代码确定性估算（不靠 LLM 张嘴）+ `estimate_basis` 口径标注 + 修订/生成双重重算**——预算与行程永远同步，偏差可知、来源可查、修正可期。
