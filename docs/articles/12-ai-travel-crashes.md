# AI 旅行翻车实录：从闭馆景点到悬崖救援，规划工具的质检底线

> 系列第 ⑫ 篇（前作 ⑪《灵感优先：AI 行程工具的入口之争》）
> 读者：做 AI 规划/生成类产品的工程师与 PM；正被「模型偶尔胡说八道」折磨的人。

## 一、先看翻车现场

2026 年真实发生的几类事故，按严重程度排：

1. **安全级**：16 岁少年用 AI 规划徒步路线被困悬崖救援（Times of India，2026-10）；Futurism 报道的 Google AI「灾难性徒步」。AI 给了一条在地图上看起来合理、实际无法通行的路线。
2. **事实级**：某工具把「昆明—大理 350km」排进半天；把周一闭馆的博物馆照常排进周一（新浪 2026-07 五工具横测）。
3. **动态事实级**：罗马九工具实测（aitravel.tools，2026-10）——全行业在「免费周日」「临时闭馆」「节假日」这类**单一动态事实**上集体翻车。Mindtrip 漏了 Colosseum 每月第一个周日免费，还把闭馆时间列错；只有 ChatGPT(web) 现场搜对了。
4. **健壮性级**：新浪横测点名三件 AI 做不好的事——**体力/天气预判**（华山估算 2h，实际走 7h）、个人偏好精准匹配、突发情况应对。
5. **商业级**：NY Post 报道「AI 规划灾难催生高价真人代理复兴」——翻车太多，用户回去找人类。

这些不是「模型不够聪明」的问题，而是**产品缺少质检层**的问题。模型可以不知道，但产品不能不知道模型不知道。

## 二、根因：LLM 的三类不确定性

把翻车归因，只有三类：

| 类型 | 例子 | 本质 |
|---|---|---|
| **事实幻觉** | 周一闭馆的博物馆排周一、列错闭馆时间 | 模型把「常见情况」当「确定事实」 |
| **数值估算** | 350km 排半天、华山 2h、预算随便写 | 模型对数字没有可靠的量纲感 |
| **动态时效** | 免费周日、临时闭馆、节假日调整 | 训练数据里没有「今天」的事实 |

对应的工程答案也很清楚：

- 事实 → **确定性规则库 + 可回溯标注**，不靠模型自觉；
- 数值 → **代码计算**，LLM 只做理解与编排；
- 动态 → **规则特例表 + 诚实提示**，把「不确定」显式暴露给用户，而不是假装知道。

## 三、我们的质检底线（都是确定性代码）

以下全部来自 my-trip-planner 仓库的真实实现，不是设计稿。

### 3.1 四维质检：让「生成者」和「审查者」不是同一个

`backend/app/agent/agents.py` 里 Planner 产出后，单独调用 `TravelCriticAgent` 按 **schedule / budget / geography / logistics** 四维打分：

- 低于 80（`CRITIC_PASS_SCORE`）→ 把结构化 issues 反馈给 Planner 重生成，最多 2 轮；
- 达上限强制定稿，但保留告警；
- Critic 自己失败 → 降级放行（质检是质量优化，不是单点故障）。

关键设计是**角色分离**：生成者和审查者用不同的 system prompt、独立调用。让模型审自己，等于让它把同一套盲点再走一遍。

### 3.2 时间真实度（TimeGate）：闭馆到达 + 单日过饱和

`backend/app/services/time_validation.py`：类目基准营业时段表（`OPEN_HOURS_BY_TYPE`）+ 建议游玩时长表，做两件确定性校验：

- **闭馆到达**：推算到达时刻距闭馆不足 30 分钟 → warning；
- **单日过饱和**：>5 站或游玩时长合计 >480 分钟 → warning。

三个诚实约束：显式 `open_hours` 优先于规则库；未知类目保持沉默（**绝不编造时间**）；结果标 `basis=rule_based`。

### 3.3 体力负荷（新增）：华山 2h vs 实际 7h 的工程回答

同一文件的 `EXERTION_BY_TYPE` 系数表 + 名称关键词规则库：

```python
EXERTION_BY_TYPE = {"hiking": 2.5, "mountain": 2.2, "attraction": 1.0,
                    "museum": 0.8, "food": 0.4, "hotel": 0.0, ...}
HIGH_EXERTION_THRESHOLD = 1.8
MAX_EXERTION_POINTS_PER_DAY = 720
```

单日体力负荷 = Σ(站点时长 × 强度系数)，超 720 提示「当日体能压力偏大」；含高强度站点（华山/徒步/雪山/峡谷）时提示「实际耗时可能显著上浮」。规则只做提示不做裁决——真实体力因人而异，诚实地写在 `basis` 里。

### 3.4 动态事实（新增）：罗马九工具集体翻车的那一格

`backend/app/services/dynamic_facts.py` 用「行程日期 × POI 特例规则表」覆盖三类动态事实：

- **周一闭馆**（故宫/博物馆/美术馆类）：日期落在周一 → 该站当天闭馆，建议改期；
- **每月免费日**（每月第一个周日）：命中 → 提示可省钱但要预约；
- **节假日窗口**：开放时间可能调整 → 提示核对官方安排。

规则库不精确判断调休——它说的是「节假日窗口建议提前预约并核对」，而不是假装知道今年怎么调休。

### 3.5 自驾约束（DrivingGate）：安全级校验

`backend/app/services/driving_service.py`：单段 120km / 150min、单日累计 300km、折返检测。超限标记 critical 反馈重生成；对话式修订同样受该门约束——**加一个远距站点不会静默落库**。

### 3.6 可回溯：每个错误答案都能查到哪一步

全程 T-A-O 轨迹（Thought-Action-Observation）随任务状态返回前端；质检报告、时间校验、自驾报告、动态事实都作为 artifact 挂在计划上。用户看到的不是「AI 说的」，而是「AI 说的 + 依据 + 哪几条警告」。

## 四、一个容易忽略的设计：降级链

OTA 有人工兜底（携程定制师、马蜂窝指路人），开源自托管工具没有。我们的兜底是**显式的降级路径**：

```
主 LLM → 重试（指数退避）→ 熔断 → provider 兜底链 → 数据源降级（高德→Tavily/wttr.in）
     → 质检失败降级放行 → 确定性 Plan B 备选 → 事件流把变更告诉用户
```

原则：**坏答案比没答案更危险**，所以每一层都写清楚「失败时往哪退、退到什么」，且每一步都有结构化日志可查。

## 五、给同行的三条可操作建议

1. **把「LLM 不该做的事」列成清单**：数值计算、事实断言、动态时效——见到就换成代码或规则库，不要试图用 prompt 修。
2. **给每个 warning 标来源**：`basis=rule_based` / `source=amap` / `source=llm`。用户能自己判断该信几分，这比「AI 说没事」值钱。
3. **未知就沉默**：未知类目不要编营业时间，无坐标不要编车程。沉默的成本远低于编错的成本。

## 六、2026-11 三更：43% 规划日带缺陷——量化的质检实证

前面五节的翻车案例都是「横测点状观察」。2026-09-08 上线的一份量化研究把「AI 行程到底错多少」变成了可检验的数字：MonkeyEatingMango 对自家 planner 生成的 **356 份真实行程、2,735 个规划日、268 个目的地、61 国**做全量缺陷审计（11 月被 Reddit/多家横评广泛引用）——结论是 **43% 的规划日带至少一个可验证缺陷**。缺陷判定全部**对照外部数据源**（live venue listing 的营业时间/永久关闭 + 路线距离计算），不读模型自述文本：这正是「质检是工程」的实证版本。

### 6.1 六类可复现失败模式

| # | 模式 | 检出数 | 占 2,735 天比例 | 一句话 |
|---|---|---|---|---|
| 1 | 到访时场馆关闭（含关门后到达） | 672 | 22.7% | 最大单一模式，其中 381 起早到（56.7%）、149 起晚于关门（22.2%）、113 起排在不开放日（16.8%） |
| 2 | 参观超过闭馆时间 | 466 | 16.6% | 与模式 1 合计是「时间错」主体 |
| 3 | 场馆已永久/临时关闭 | 13 | 0.5% | 量小但代价最大：Tjapukai 文化园 2021 年已永久关闭、Wajima 早市 2024 年火灾烧毁，模型照排 |
| 4 | 同一地点重复安排 | 169 | 5.1% | 3 天行程重复率 6.2%、15 天以上飙到 56.2%；57% 的重复落在相邻两天内 |
| 5 | 当天路线折返 | 261 | 9.5% | 中位多走 3.4km、最严重 40km、合计约 1,480km；被标记的 261 天里 142 天只有 3 站 |
| 6 | 日落/日出活动排在中午 | 4 | 0.1% | 罕见但存在；4 条里 3 条是误报（「Sunset Heights」街区午餐）——质检器也会错，要能认错 |

三组关键数字：**周一承载 53% 的闭馆类错误**（113 起闭馆日错误里 60 起是周一）；早到错误 84% 只差 1 小时以内（中位 60 分钟）——差得不多，但足以让四口之家站在周一闭馆的博物馆门口；**重复与时间错强关联**（有重复的行程中 93% 同时有时间错、81% 有超闭馆时间访问）——模型在长行程里「抓不住」是同一根因，折返则独立于一切。

### 6.2 修复率：检出-修复闭环是可度量的

同一份研究给出正向侧：**1,324 处排程缺陷被检出，1,054 处在交付前修正，修复率 79.6%**；319 个受影响行程中 182 个（57%）交付时零残留缺陷；修不掉的就**红色标在活动条目上**，而不是藏起来。

这把我们 3.1 节的「角色分离」设计从经验变成了可对标数字：**分段检出的 79.6% 修复率不是模型运气，是「第二遍检查」这一工程阶段的产出**。研究原文点破了机制：聊天助手写完文本，文本就是成品——没有任何一步会拿 live 数据重新读一遍、把坏的一天退回重写、或把错的地方标出来。这就是我们一直在做的质检层。

### 6.3 对照我们的实现（逐条可核验）

| 研究中的失败模式 | 我们的对应（代码在案） | 状态 |
|---|---|---|
| 模式 1/2 时间错（含周一闭馆） | `time_validation.py` TimeGate：类目基准营业时段 + 闭馆前 30 分钟 warning + `basis=rule_based`；`dynamic_facts._weekly_closed` 周一闭馆/免费日/节假日特例表（2026-11-13 已把展馆同义/纪念馆/故居/图书馆/遗址博物馆补入类目） | ✅ |
| 模式 3 永久关闭 | 零凭证规则库路线**不追踪**实时关闭状态；「未知就沉默」约定防止编造——这是已知边界，不假装覆盖 | 🟡 |
| 模式 4 重复地点 | **缺口**：目前无专责确定性去重检测器（planner 侧依赖提示词约束，未做代码级复核）——研究中重复随行程长度飙升（15 天以上 56.2%），且与时间错 93% 共现，值得单独立项 | ❌ |
| 模式 5 折返 | `day_optimizer.py` 确定性最近邻重排（首站锚定、省不到 1% 不提议、缺坐标不硬塞）+ `solver_service` 候选排序/硬约束校验/有限修复（`solver_meta` 不伪装成功）——「把一天当路线而不是清单」我们的工程回答 | ✅ |
| 模式 6 时间语义错 | `weather_validation.py` 只做有数据才提示、`basis=weather_forecast` 诚实标注，不给假精度 | ✅ |
| 修复率 79.6% 对应 | `agents.py` Critic 四维质检：<80 分反馈重生成（最多 2 轮）、达上限强制定稿但保留告警、Critic 失败降级放行 | ✅ 对标 |

### 6.4 三个比数字更重要的提醒

1. **质检器自己也会错**（4 条日落发现里 3 条误报），但模型正确拒绝了「Sunrise Point 观景点」这类地名陷阱——规则要配「可拒绝」的权限，不是发现即改。
2. **重复的规律可防**：多在长行程后段出现（第 9 天重复率 21.1%）且爱挨着出现（57% 在两天内）——确定性查重按「相邻两天窗口」扫描就够，不需要全局重规划。
3. **「带引用」不等于可靠**：模式 3 的 13 处关闭场馆全部来自 live listing 核验，而模型训练文本里 Tjapukai 依然「活着」——引用训练语料和核对实时事实是两回事（13 文诚实边界一节会继续展开）。

一句话：43% 不是「模型不够聪明」的判决书，而是**「没有第二遍检查」的施工图**——每一条都能对到确定性的检查项上，也都能修。

## 七、小结

> AI 旅行产品的质检底线不是「更聪明的模型」，而是：**事实用规则、数字用代码、动态用特例表、失败有降级、结论有来源。**

翻车不可怕，可怕的是翻车了产品不知道。下一篇讲信任缺口：为什么「第一次尝试就翻车」是产品问题，以及我们怎么把「可验证」做成可感知的。
