# 终局剧本：当 agentic 预订已经成交、独立工具已被收购——规划层还剩什么

> 写给：AI 旅行/规划类产品的产品经理和工程师，以及所有在「巨头 + 资本」牌局里找位置的独立开发者。
> 一句话结论：2026 年 AI 旅行赛道已经写完了「终局剧本」的前三幕——agentic 预订在对话里成交、独立规划工具被 OTA 收购、撑不住的玩家无声退场。独立的规划层没有消失，它被重新定价了：**不再是「等被收购的过渡形态」，而是「小而锋利」的长期生意**——可修订、可验证、可协作、输入自由。本文用四个真实事件收束系列（07/08 姊妹篇），并把「终局之后还能做什么」落成我们仓库里的具体实现。

## 一、终局四幕：2023 到 2026 的完整时间线

### 第一幕：病毒式 demo 的退场（Tripnotes，2023-12）

Tripnotes 是 ChatGPT 时代的明星：一个 demo 视频病毒式传播，几十万用户涌入，产品从「AI 生成行程」出发，几乎定义了最初的品类叙事。但融资冰点期没有撑住，2023 年底被 Dorsia（会员制餐厅预订）收购后关站。创始团队转去做了高端餐厅预订——**规划工具的第一笔终局交易，是以「关站」完成的**。

### 第二幕：对话内成交（Mindtrip Flights，2026-05）

Mindtrip 上线行业首个 agentic 机票预订：Sabre Mosaic（420+ 航司实时库存/占座）提供交易轨，PayPal 对话内结账（含 BNPL Pay in 4 / Pay Monthly），用户在聊天框里完成「搜索 → 比价 → 支付 → 出票」全程，不跳第三方站。规划本身免费无 paywall，视觉精美，数据与预订集成最深。这是「从灵感直接到交易不出聊天框」的完整商业闭环。

### 第三幕：规划工具并入预订巨头（Expedia × Layla，2026-07-31）

Expedia Group 官宣收购 Layla（2023 年创立、约 25 人、约 €5M 融资、金额未披露、继续 standalone 运营）。Layla 的招牌是对话式规划 + 实时价格（Skyscanner/Booking.com）+ PriceLock 提醒，免费起步、Premium $49/年；1.1M+ 行程、自报 4.9 星；收购加速 Expedia 多智能体架构（此前 deprioritize Romie，转向 specialized agents）。**规划工具的第二笔终局交易，以「并入库存 + 支付集团」完成**。

### 第四幕：无声倒闭（Troupe，2026-06）

JetBlue 旗下群组规划 Troupe 确认倒闭：域名不解析、双商店下架、无官方公告。它的替代者 TRIPTI.ai 有一个关键架构洞见：**「多数 commit 即锁定日期，不要求全员同意」**（progressive vs consensus-first）——「不回复的那个人不冻结整个行程」。JetBlue 都做不活的群组规划，恰恰说明协作刚需持续存在，但产品必须轻、必须渐进。

> 把四幕连起来看：**独立规划工具的剧本从来只有两本——被巨头整合，或小而锋利地活。** 预订层正在「对话内成交 + 巨头整合」双轨加速，而纯功能型规划工具的窗口正在关闭。

## 二、终局之后的牌局：预订层还剩什么（以及为什么小团队不该上桌）

预订层的三件事，每一件都是资本密集型生意：

| 层 | 玩家 | 核心资产 | 小团队可行性 |
|---|---|---|---|
| 库存/交易轨 | Sabre/Amadeus/GDS、OTA 直连 | 实时库存、占座、退改规则 | ❌ 需要多年供应链谈判 |
| 支付/合规 | PayPal/Stripe/BNPL、PCI、各市场税规 | 支付牌照、风控、货币/税务 | ❌ 合规成本即门槛 |
| agentic UI | Mindtrip/Layla/Expedia | 对话式预订体验 + 推荐分发 | 🔶 UI 能做，但上面两层不归你 |

Mindtrip × Sabre × PayPal 的三层分工说明：**预订层没有一层是小团队能自建的**——这不是 prompt 能补齐的差距，是「库存 + 支付」的资金和合规壁垒。而把规划工具卖给 OTA 的那笔交易（Layla），买家买的也不是规划能力，是**用户入口**：一个已经信任「AI 帮我定行程」的流量池，用来喂预订漏斗。

**所以终局之后，规划层还剩什么？** 剩的是预订层玩家**结构性不愿做、也做不好**的事：

- **不愿做**：可修订。改行程动了他们的库存和佣金，预订闭环的组织复杂度决定规划只能做入口。
- **做不好**：可验证。实时库存决定了「推荐 = 可售商品」，而不是「对你最好的安排」。
- **被商业模型锁死**：透明。库存、价格、支付都是商业机密，OTA 永远无法开源「为什么推荐这个」。
- **最后的输入自由**：笔记/截图/邮件文本导入。用户真实世界的信息（攻略、种草、确认邮件）不属于任何库存体系，是规划层独占的入口。

## 三、我们怎么接住这个终局：五根支柱（对应仓库实现）

我们（my-trip-planner，FastAPI + LangGraph + Vue3，开源于 github.com/TonyJun18/my-trip-planner）没有任何预订功能，全部资源压在规划层的五根支柱上。以下代码引用均与仓库实际一致（main 分支，2026-10 时点）。

### 支柱一：可修订——AI 出 diff，代码执行

预订层产品怕用户改（改了要重算价格库存），规划层产品应该欢迎用户改。我们把「改行程」做成一等公民：

```python
# backend/app/services/revise_service.py
async def revise_trip(db, trip_id, message, *, owner=None, provider="auto"):
    # 1) AI 只生成结构化 diff（PlanReviseAgent，无工具、失败可自纠正）
    revise = await plan_revise_agent({...}, current_plan, provider=provider)
    # 2) 代码原子应用（存在性/类型/位置校验，任一失败整体回滚）
    _apply_diff(trip, diff)
    # 3) 落库 + 预算代码重算（LLM 估值不可信）
    await _recompute_budget(db, trip)
    await db.commit()
```

修订在 2026-09 系列里是第四篇的主线，这里只补一层新的事实：**修订已经升级为「质控闭环」**。2026-10 起，修订后由 ReviseCriticAgent 复审（Evaluator-Optimizer，最多 2 轮）：未通过且可精确修复 → Critic fix 转可执行 diff 原子应用 → 复审；无 fix/停滞/自驾约束拒绝 → 有界停止；Critic 熔断/超时降级为通过，绝不阻断合法修订。**修订不再是单程票，而是有质检闸门的闭环**（`backend/app/agent/agents.py` 的 `REVISE_CRITIC_SYSTEM_PROMPT` / `_revise_qa_loop`，测试 `test_revise_qa_loop.py` 9 例）。

### 支柱二：可验证——价格真实度与质检闭环

价格真实度：酒店参考价用代码确定性估算，不靠 LLM 瞎报：

```python
# backend/app/services/budget_service.py
def estimate_hotel_cost(name, city=None, *, rating=None) -> float:
    base = _HOTEL_CITY_BASE.get(_match_city(city), _HOTEL_FALLBACK)  # 城市基准价
    multiplier = 1.0
    for kw, m in _HOTEL_TIER:            # "五星"×2.8、"经济"×0.7 ……
        if kw in name:
            multiplier = m
            break
    ...
```

城市基准价 × 档位倍率 × 评分修正——**可解释、可测试、不依赖外部价格源**，前端标注"参考价，以实际询价为准"。预算口径随预算一起返回（`estimate_basis`：来源/基准/置信度），修订后代码重算（`revise_service._recompute_budget`）——任何时候用户看到的预算，都是当前行程在代码口径下的确定性结果。玩「预算游戏」的竞品（低估预算引客）在这里没有操作空间。

质检闭环：Planner 产出后由 TravelCriticAgent（无工具质检专家）按日程/预算/地理/完整性四维评分，不过审带反馈重生成（最多 2 轮后强制定稿，质检失败自动降级放行）。配合前端实时 T-A-O（Thought-Action-Observation）轨迹（`frontend/src/views/PlanWizard.vue`），**用户能看到每个 Agent 在干什么、为什么这么生成**——黑盒是规划层最大的信任杀手，透明是免费工具最便宜的护城河。

### 支柱三：可协作——把多人决策留在规划层

多人出行是高频刚需，但群组共编 (co-edit) 复杂度高。我们做轻量协作：分享链接 + 评论 + 站点 👍/👎 投票（凭 share_token 免登录、投票幂等可翻转、同行程归属校验）：

```python
# backend/app/services/collab_service.py
async def _belongs_to_trip(db, stop_id, trip_id) -> Stop:
    """校验站点属于该行程（防止跨行程投票）。"""
    stmt = (select(Stop).join(TripDay, TripDay.id == Stop.id)
            .where(Stop.day_id == day_id, TripDay.trip_id == trip_id))
    ...
```

一行 `share_token` + 一组轻接口，就把"群里十个链接来回发"变成"一个链接大家投票定行程"。分享链接还支持「受邀编辑权」（edit_token 与只读 share_token 分离，受邀者可改站点顺序/备注/勾选，owner 可收回）。对照 Troupe 的教训，协作的验收口径是 TRIPTI.ai 式的**渐进式推进**：投票/确认达到 ≥50% 受邀成员即可标记「小组一致」，未响应成员不阻塞后续——「不回复的那个人不冻结整个行程」。

### 支柱四：输入自由——把用户真实世界的信息接进来

笔记/种草文本导入（Tripnotes 范式复活）：粘贴攻略笔记 → 结构化提取站点候选 → 勾选并入行程：

```python
# backend/app/services/note_import.py
def parse_note(text: str) -> NoteImportResult: ...
```

预订后整理（iGo/TripNoted 的 post-booking 范式，零凭证粘贴版）：粘贴预订确认邮件文本 → 复用 note-import 敌意输入处理管线，识别航班/酒店/活动条目（日期时间/名称/地址/确认码/金额）→ 候选勾选并入行程。2026-10 已实现入 main：

```python
# backend/app/services/email_import.py
def parse_email(text: str) -> EmailImportResult: ...
# 航班行：国航 CA1234 / 东航 MU5101 / 南航 CZ3456 等两字母+3~4位数字
# 确认码/订单号：预订编号 / 确认号 / 确认码 / 订单号 / 预订号 / booking ref
# 酒店名：杭州西湖大酒店（「酒店名」+ 酒店/民宿/客栈/宾馆/饭店/度假村 后缀）
```

为什么「输入自由」是终局后的关键支柱？因为**确认邮件、攻略笔记、种草链接这些信息不属于任何库存体系**——它们是用户真实生活的沉淀，OTA 的 agentic 预订拿不到，规划层独占。Mindtrip 的对话内成交解决的是「怎么买」，输入自由解决的是「拿什么规划」——后者恰恰是预订巨头没动力做深的空地。截图/社交链接导入也在管线内（OCR 主路径 + 链接提取降级分支，队列中）。

### 支柱五：可自托管——开源是规划层的天然护城河

预订层永远无法开源（库存、价格、支付都是商业机密）。规划层可以。我们把整个仓库 MIT 开源，用户自己 `docker compose up` 就能跑起来——没有账号墙、没有数据锁定、没有"你的行程是别人家的流量"。对独立开发者和小团队来说，**开源不是情怀，是把「透明」这个规划层优势资本化**：预订层玩家被商业模型锁死不能做的事，我们天然能做。

## 四、可复用的模式

| 决策 | 落地方式 | 收益 |
|---|---|---|
| 不碰预订闭环 | 只做规划层（生成/修订/质检/协作/自托管/输入自由） | 避开库存+支付重资产，专注体验 |
| 修订做成质控闭环 | ReviseCriticAgent ≤2 轮 + fix 转 diff 原子应用（agents.py / revise_service.py） | 修订质量有闸门，不无限烧 token |
| 价格用代码估算 | 城市基准价 × 档位倍率（budget_service.py）+ estimate_basis 口径标注 | 可解释、可测试、无外部依赖 |
| 协作做轻量版 | share_token + 评论 + 投票 + 受邀编辑权（collab_service.py） | 多人决策可闭环，不碰协同编辑复杂度 |
| 渐进式推进 | 投票 ≥50% 标记「小组一致」，未响应不阻塞 | 不回复的人不冻结行程（TRIPTI 教训） |
| 输入自由 | note_import.parse_note + email_import.parse_email（敌意输入同管线） | 真实世界信息接进来，OTA 拿不到 |
| 透明做资本化 | MIT 开源 + T-A-O 轨迹 + 参考价标注 | 预订层玩家锁死不能做，我们天然能做 |

**最关键的迁移心态**：终局之后不要再问「规划层还能不能独立活」——答案已经写在四幕里：被收购的是入口，不是能力。问自己一个问题：**你的产品在「计划-预订」链路上，是做入口的那段，还是做能力的那段？** 预订层把入口做成了漏斗，我们把入口做成了产品。

## 五、给同行的一份「终局检查清单」

1. **你的产品在被收购清单上吗？** 如果价值 = 流量入口，终局大概率是被并入预订巨头，且这不是你能决定的。
2. **你碰预订了吗？** 碰了，请备好库存、支付、售后和资金——那是另一个量级的生意。
3. **你欢迎用户改吗？** 欢迎（diff + 原子应用 + 回滚），预订层怕改，规划层的壁垒就在"敢让用户改"。
4. **你的价格敢亮口径吗？** `estimate_basis` 式透明，还是玩低估预算的漏斗游戏？
5. **你接住用户真实世界的信息了吗？** 笔记/截图/确认邮件——这些不属于任何库存体系，是规划层独占的入口。
6. **你开源了吗？** 预订层永远无法开源。开源是规划层的结构性特权，不用白不用。

## 小结

- 2026 年 AI 旅行赛道写完终局剧本的前三幕：**Mindtrip 对话内机票成交**（Sabre + PayPal）、**Expedia 收购 Layla**（入口并入库存与支付）、**Tripnotes 关站 / Troupe 倒闭**（退场是无声的）。
- 预订层是资本密集型生意（库存/支付/合规），独立工具的正解是把规划层做深：**可修订（diff + 原子应用 + 质控闭环）、可验证（价格口径 + 质检 trace）、可协作（轻量投票 + 渐进式推进）、输入自由（笔记/邮件文本导入）、可自托管（开源）**。
- 规划层不是"等被收购的过渡形态"——**被收购的是入口，不是能力**；小而锋利地活，就是把预订层玩家结构性不愿做、做不好、被商业模型锁死的事，做到竞品做不到的深度。
